Threading / Concurrency Dependency

Java dependency type · Modern Java technique: Inject an Executor

The dependency
Threading / Concurrency Dependency
The technique
Inject an Executor
Not in Chapter 25. Feathers' catalog treats concurrency as a design concern that resists individual dependency-breaking techniques. The modern Java answer — inject the Executor so tests can run submitted tasks synchronously — applies Feathers' Parameterize Constructor principle to the specific case of async work. CompletableFuture (Java 8, 2014) and Executors (Java 5, 2004) give this approach a standard shape the book couldn't have covered.
Scope: "where does work run?" This page covers the case where your code produces async work — spawns threads, submits to executors, calls CompletableFuture.runAsync. The sibling page Async Result Dependency → Supply Pre-Completed Results covers the opposite shape: your code consumes async results from a collaborator that returns CompletableFutures or calls back. Both patterns often appear in the same class, and both benefit from being tested with deterministic stand-ins — but the seams are different and the fakes look different.

The dependency

A threading / async dependency appears whenever code starts its own asynchronous work: new Thread(r).start(), Executors.newSingleThreadExecutor().submit(task), CompletableFuture.runAsync(r), CompletableFuture.supplyAsync(supplier), any @Async method, any scheduled task. The class decides where and when the work runs, and tests inherit that decision.

Common shapes: fire-and-forget background writes, parallel data enrichment, delayed retries, timeout-bounded calls, event publishing. All of them launch work the caller doesn't wait for — and tests, by default, either return before the async work finishes (and assert on stale state) or block on arbitrary sleeps (and become flaky).

Why this blocks tests

The test returns before the work does

Code like CompletableFuture.runAsync(() -> audit.record(entry)) schedules a task and returns immediately. A test that calls the enclosing method and then asserts on the audit log often sees an empty log — the task hasn't run yet. The audit actually lands a few milliseconds later, after the assertion has already failed.

Sleep-based synchronization is a lie

The common workaround — Thread.sleep(100) before the assertion — is wrong in both directions. On a fast machine, 100ms is overkill and wastes test-suite time. On a slow or loaded CI runner, 100ms isn't enough and the test fails intermittently. Neither outcome is a real signal.

Thread scheduling is non-deterministic

Two async tasks that complete in one order on your laptop can complete in the opposite order in CI. Tests that assume a particular completion sequence pass locally and fail on the shared runner, eroding team trust in the suite.

Error paths in async code are effectively untestable

Testing "what happens when the async task throws" requires both making it throw and waiting long enough for the throw to propagate through the CompletionStage chain. With a real executor and real timing, both halves are fragile.

Default executors are shared

CompletableFuture.runAsync(r) without an explicit executor uses ForkJoinPool.commonPool(). Every test that touches such code shares that pool with every other test in the JVM, and with the test framework itself. Contention produces flakiness; one misbehaving test's leftover task can affect the next.

The technique: Inject an Executor

Inject an Executor makes the class's async behavior a parameter instead of a hard-coded choice. The class takes an Executor (or ExecutorService, or ScheduledExecutorService, depending on the scope) through its constructor. Production wires in a real pool; tests wire in a synchronous executor — one that runs each submitted task on the caller's thread, immediately, before execute returns.

With a synchronous test executor, async code becomes effectively sequential during tests: the submitting method waits (implicitly) for the task to complete, the test sees the effects, and every assertion is deterministic. Everywhere a CompletableFuture would have been pending, it's already complete.

When to use it

  • A class spawns its own threads or submits to ForkJoinPool.commonPool() / similar default pools.
  • Tests need to assert on the effects of async work deterministically.
  • You can change the class's construction to accept an executor.

When not to use it:

  • The class's purpose is concurrency — a throttling rate-limiter, a parallel work-stealing scheduler. Tests should exercise real concurrency with real executors.
  • The async behavior is orthogonal to what you want to test — consider separating the async wrapper from the synchronous core and testing the core directly, with no executor at all.

Example

Before — NotificationService sends email asynchronously using the default pool:

public class NotificationService {
    private final EmailSender email;
    private final AuditLog audit;

    public NotificationService(EmailSender email, AuditLog audit) {
        this.email = email;
        this.audit = audit;
    }

    public CompletableFuture<Void> notify(User user, Event event) {
        return CompletableFuture.runAsync(() -> {
            email.send(user.getEmail(), event.asMessage());
            audit.record("notified:" + user.getId());
        });
    }
}

A test calling notify and immediately checking the audit log races the async work. Adding .get() on the returned future helps, but only for the happy path — it won't make two concurrent notifications complete in a predictable order, and it introduces blocking into a test that was supposed to be fast.

Steps

  1. Identify the async primitive: explicit thread creation, ExecutorService submission, CompletableFuture.runAsync, @Async method.
  2. Add an Executor constructor parameter. For simpler cases, Executor is enough; for scheduled work, take ScheduledExecutorService.
  3. In the class body, pass the injected executor explicitly: CompletableFuture.runAsync(task, executor), executor.execute(runnable).
  4. Provide a convenience no-arg constructor (or production wiring) that supplies the real pool.
  5. In tests, pass a synchronous executor — either Runnable::run as an Executor, or a named implementation (DirectExecutor — see below).

Example (after)

public class NotificationService {
    private final EmailSender email;
    private final AuditLog audit;
    private final Executor executor;

    public NotificationService(EmailSender email, AuditLog audit, Executor executor) {
        this.email = email;
        this.audit = audit;
        this.executor = executor;
    }

    public CompletableFuture<Void> notify(User user, Event event) {
        return CompletableFuture.runAsync(() -> {
            email.send(user.getEmail(), event.asMessage());
            audit.record("notified:" + user.getId());
        }, executor);
    }
}

// Minimal synchronous executor — runs tasks on the calling thread
public class DirectExecutor implements Executor {
    @Override
    public void execute(Runnable r) { r.run(); }
}

// Test — async behavior becomes deterministic
@Test
public void notifySendsEmailAndRecordsAudit() throws Exception {
    FakeEmailSender fakeEmail = new FakeEmailSender();
    FakeAuditLog fakeAudit = new FakeAuditLog();
    Executor sync = new DirectExecutor();

    NotificationService svc = new NotificationService(fakeEmail, fakeAudit, sync);
    svc.notify(User.withEmailAndId("a@b.com", "u-1"), Event.sample()).get();

    assertEquals("a@b.com", fakeEmail.lastRecipient);
    assertEquals("notified:u-1", fakeAudit.lastEntry);
}

@Test
public void notifyPropagatesEmailFailures() {
    EmailSender failing = (to, msg) -> { throw new SmtpDownException(); };
    NotificationService svc = new NotificationService(failing, new FakeAuditLog(), new DirectExecutor());

    CompletableFuture<Void> f = svc.notify(User.sample(), Event.sample());

    assertTrue(f.isCompletedExceptionally());
}

Supporting and alternative techniques

Separate the async wrapper from the synchronous core

Often the cleanest design is to put all the interesting logic in a method that runs synchronously and is tested without any executor, then have a thin async wrapper method that simply submits the sync method to the executor. The wrapper is trivial — one line — and barely needs testing. The core is 100% testable without touching concurrency. This mirrors the general advice "keep concurrency at the edges".

public CompletableFuture<Void> notify(User u, Event e) {
    return CompletableFuture.runAsync(() -> notifySync(u, e), executor);
}

void notifySync(User u, Event e) {  // package-private for tests
    email.send(u.getEmail(), e.asMessage());
    audit.record("notified:" + u.getId());
}

A deferred-execution test executor

When you need to test task ordering — "task A should have submitted task B before completing" — a synchronous executor isn't enough. Write a DeferredExecutor that queues tasks and only runs them when the test explicitly calls runAll(). This lets the test inspect the queue between runs.

Guava's MoreExecutors.directExecutor()

If your project already depends on Guava, skip the hand-written DirectExecutor: MoreExecutors.directExecutor() returns a canonical singleton. Small time saver; not a different technique.

Extract and Override Call

For a single async call site you'd rather not wire into the constructor, Feathers' Extract and Override Call works: wrap the runAsync in a protected method and override it in a test subclass to run the task synchronously.

Cautions and variations

Synchronous tests do not test concurrency

The synchronous executor makes async code deterministic, but it doesn't verify the code is correct under real concurrency. Race conditions, deadlocks, and memory-visibility bugs are invisible to a synchronous test. For genuine concurrency testing, different tools apply — jcstress for memory models, stress tests for races — and they complement, rather than replace, the deterministic unit tests.

Don't hold the executor yourself

The class under test should accept the executor, not construct it. An injected Executor is managed by whoever created the class — usually the composition root — and gets a consistent lifecycle. A class that constructs its own pool leaks threads on every instance.

Shutdown lifecycle matters

For ExecutorService (which has shutdown semantics), decide clearly who owns the lifecycle. If the class takes one, it shouldn't shut it down — that responsibility belongs to the code that created it. Otherwise tests that create a fresh executor per test and shut it down between tests start to interfere with long-lived production code when the patterns mix.

Spring's @Async

In Spring, @Async-annotated methods delegate to a TaskExecutor bean. Tests that want deterministic behavior either override that bean with a SyncTaskExecutor or (cleaner) call the underlying synchronous method directly, bypassing the Spring proxy. Either way, the principle is the same: make the executor a parameter of the system, not a fixed constant.
