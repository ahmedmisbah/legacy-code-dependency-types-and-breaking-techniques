Final / Sealed Dependency

Java dependency type · Modern Java technique: Wrap with a Hand-Written Adapter

Not in Chapter 25. Feathers' Subclass and Override Method assumes the class isn't final and the method isn't final. Extract Interface assumes you own the source and can add implements. When both assumptions fail — which is the normal case for third-party library classes, many JDK types, and Kotlin-compiled code that defaults to final — neither technique applies. The modern Java workaround is an adapter you control, possibly combined with Mockito's bytecode-level mock-maker-inline extension when hand-writing an adapter would be overkill.

The dependency

A final / sealed dependency exists when your code depends on a type that's closed to extension: marked final, marked sealed without your class in the permits list, or containing final methods at the points you need to override. JDK examples include String, Integer, Pattern, LocalDateTime, URI, and Optional. Third-party examples include many Guava types, vendor SDK clients, and Kotlin classes (which are final by default unless marked open).

The seal is usually deliberate: immutability, security, performance, or API-evolution safety. The designers want to prevent misuse — but the same seal prevents the subclass-and-override trick that testability techniques lean on. Your code that collaborates with the sealed type has the whole class as a hard dependency, with no standard seam.

Why this blocks tests

Subclass and Override Method doesn't compile

The single most common Feathers technique — make a test subclass, override the problem method — fails at the compiler. You get Cannot inherit from final class or Cannot override the final method. There's no way around it through ordinary Java.

Extract Interface requires modifying the class

To let a class implement an interface, you'd have to add implements YourInterface to its declaration. For a class you don't own, that's impossible. You can extract an interface with the same shape as the class's API, but the sealed class itself won't implement it, so you can't pass a sealed instance where the interface is expected.

Standard mocking frameworks have limits

Default Mockito (without the inline mock-maker) can't mock final classes. Bytecode-generation libraries it relies on — CGLIB, Byte Buddy with the default mock-maker — create subclasses, which fails on sealed types. Mockito's mock-maker-inline extension uses the JVM's instrumentation API to rewrite bytecode and can mock final classes, but it adds startup cost and fragility.

Construction is often awkward too

Sealed types frequently have non-public or context-dependent constructors. Even if you could subclass, constructing real instances in tests may require setting up the context the class's design expected.

The technique: Wrap with a Hand-Written Adapter

Wrap with a Hand-Written Adapter creates a type you control between your code and the sealed type. You define an interface declaring just the methods your code uses. You write an adapter class that implements the interface by delegating to the sealed type. Your code accepts the interface, not the sealed type. In production, construct the adapter around a real instance; in tests, implement the interface directly with a fake.

This is Adapt Parameter from Ch 25 applied specifically when the motivation is the seal rather than the class's size or API surface. The mechanical moves are the same; the decision criteria are different (finality forces your hand; API surface is a judgment call).

When to use it

  • Your code depends on a final or sealed class (or one with final methods you need to vary).
  • You can change your code to accept an interface instead of the concrete type.
  • The class's useful surface (to your code) is small — a few methods, not the whole API.

When not to use it:

  • The class is barely used (one call, no varying behavior needed) — consider Parameterize Method or simply accepting the dependency without mocking.
  • The class is pervasive through your codebase (e.g., String) — wrapping it would be absurd. These are typically already testable by just passing different values.
  • Mockito's inline mock-maker is already in the project and fast enough — pragmatic shortcut, discussed below.

Example

Before — InvoicePrinter depends on a vendor PdfRenderer that's declared final:

// Vendor library, not yours
public final class PdfRenderer {
    public PdfRenderer(PdfConfig config) { // heavy init, loads fonts, etc. */ }
    public byte[] render(Document doc) { // real rendering */ }
    public void attachFont(Font font) { /* ... */ }
}

public class InvoicePrinter {
    private final PdfRenderer renderer;

    public InvoicePrinter(PdfRenderer renderer) { this.renderer = renderer; }

    public byte[] print(Invoice invoice) {
        Document doc = buildDocument(invoice);
        return renderer.render(doc);
    }
}

You can't subclass PdfRenderer. You can't add an interface to it. Instantiating a real one in tests is slow and loads fonts from disk. The document-building logic — the part worth testing — is hostage to the renderer.

Steps

  1. List the methods your code calls on the sealed type. For InvoicePrinter, just render.
  2. Define an interface containing those methods, named for the role (DocumentRenderer) rather than the vendor.
  3. Write a small adapter implementing the interface by delegating to the sealed type. Give it a constructor that takes the sealed instance.
  4. Change your code's constructor parameter type from the sealed class to the interface.
  5. At production construction sites, wrap the sealed instance: new InvoicePrinter(new VendorPdfAdapter(pdfRenderer)).
  6. In tests, implement the interface directly with a fake.

Example (after)

// Interface you own
public interface DocumentRenderer {
    byte[] render(Document doc);
}

// Adapter that delegates to the sealed vendor type
public class VendorPdfAdapter implements DocumentRenderer {
    private final PdfRenderer vendor;

    public VendorPdfAdapter(PdfRenderer vendor) { this.vendor = vendor; }

    @Override
    public byte[] render(Document doc) { return vendor.render(doc); }
}

// Code under test takes the interface
public class InvoicePrinter {
    private final DocumentRenderer renderer;

    public InvoicePrinter(DocumentRenderer renderer) { this.renderer = renderer; }

    public byte[] print(Invoice invoice) {
        Document doc = buildDocument(invoice);
        return renderer.render(doc);
    }
}

// Test — no vendor library, no font loading
@Test
public void printRendersBuiltDocument() {
    DocumentRenderer fake = new DocumentRenderer() {
        public Document captured;
        @Override
        public byte[] render(Document doc) {
            captured = doc;
            return new byte[] { 0x25, 0x50, 0x44, 0x46 }; // "%PDF"
        }
    };

    InvoicePrinter printer = new InvoicePrinter(fake);
    byte[] pdf = printer.print(Invoice.sample());

    assertEquals(4, pdf.length);
}

Supporting and alternative techniques

Mockito mock-maker-inline

A pragmatic shortcut when you have many sealed types and writing adapters for each would be costly. Adding org.mockito:mockito-inline to the build (or enabling the inline mock-maker in mockito-core 5+) lets Mockito mock final classes via JVM instrumentation. Tests can then write PdfRenderer renderer = mock(PdfRenderer.class) directly.

Costs: slightly slower test startup, occasional compatibility issues across JVM versions, and a framework dependency the test reads like "this class shouldn't normally be mockable; Mockito is doing something special". The hand-written adapter is cleaner for the small number of sealed types your code genuinely depends on; the inline mock-maker is a reasonable fallback for the rest.

Adapt Parameter (the Ch 25 sibling)

This page's technique is functionally identical to Adapt Parameter — the difference is motivation. Adapt Parameter is typically described for wide API surfaces where an interface extraction is impractical; the final/sealed page emphasizes that extraction is impossible, not merely awkward. When in doubt, read both pages.

Subclass and Override Method with open Kotlin classes

If the sealed type comes from a Kotlin module you control, changing the class declaration from default-final to open removes the problem at the source. This is often the right fix when the code is yours and the seal was accidental rather than deliberate. For third-party classes, this path isn't available.

Cautions and variations

Name the interface by role

Don't call the interface IPdfRenderer or PdfRendererWrapper. Call it by what it does in your domain: DocumentRenderer, InvoiceRenderer, ReportExporter. The adapter name can reference the vendor (VendorPdfAdapter); the interface should name the role.

Keep the adapter thin

Each method on the adapter is one line — a direct delegate to the sealed type. Any caching, error translation, or additional logic belongs in a higher layer. A fat adapter grows its own testability problems.

Library upgrades become easier

A secondary benefit worth noting: when the vendor releases a new major version with breaking changes, only the adapter needs to track those changes. Your core logic keeps compiling unchanged. This often matters more than the testing benefit.

Don't wrap JDK value types

Classes like String, Integer, LocalDate, UUID are final but don't present testability problems — they're values, not collaborators. You "fake" them by passing different values. No wrapper needed.

Related techniques not covered here. Library / Framework Dependency → Adapt Parameter is the closest sibling — same mechanical fix, usually applied to wide-surface framework types rather than specifically to sealed ones.
