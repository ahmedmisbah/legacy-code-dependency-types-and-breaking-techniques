Randomness Dependency

Java dependency type · Modern Java technique: Inject a Random Source

The dependency
Randomness Dependency
The technique
Inject a Random Source
Not in Chapter 25. Feathers' catalog doesn't name a technique specifically for random numbers. Like time, randomness is a case of Feathers' Encapsulate Global References applied to a specific primitive — Math.random(), ThreadLocalRandom, UUID.randomUUID() — with the fix delivered via Parameterize Constructor. The shape is identical to Clock injection; only the type being injected changes.

The dependency

A randomness dependency exists wherever code calls a non-deterministic generator: Math.random(), new Random().nextInt(), ThreadLocalRandom.current().nextDouble(), UUID.randomUUID(), SecureRandom.nextBytes(...). Each call returns a value nobody can predict. The class using these calls makes decisions that cannot be reproduced.

Common places this bites: A/B test bucketing, sampling, retry jitter, shuffling, cryptographic nonces, correlation IDs, short-code generation, simulated dice rolls, load balancing, exponential backoff. Any of these, left un-injected, makes the containing class un-testable except by running many trials and asserting statistical properties — which is slow, imprecise, and often flaky.

Why this blocks tests

Every run produces a different answer

A test that exercises code branching on random.nextInt(100) < 50 hits one branch roughly half the time. A test that asserts the "heads" branch was taken either fails intermittently or spins in a loop until it happens to see heads — neither is a real test.

UUIDs make objects unequal to themselves

If a class under test stamps objects with UUID.randomUUID(), no two test runs produce the same object. Tests comparing against known-good fixtures can't use the IDs; tests capturing-then-comparing are circular.

Statistical assertions hide bugs

When teams give up on determinism, they fall back to assertions like "should be heads at least 40% of 1000 trials". These tests are slow, occasionally fail for real reasons and occasionally fail for noise, and tell you nothing about which specific path the code took.

Cryptographic code resists testing entirely

Code using SecureRandom for nonces or key material can't be unit-tested against specific outputs, because the whole point of the generator is that outputs can't be predicted. The fix is the same seam — inject a source — with extra care about what the test source is allowed to produce.

The technique: Inject a Random Source

Inject a Random Source replaces direct generator calls with calls on an injected Random (or a narrower interface). The class's constructor takes a Random; production passes new Random() or new SecureRandom(); tests pass new Random(seed) with a fixed seed, or a fake that returns canned values for each call.

For UUID.randomUUID specifically, the neat approach is to inject a Supplier<UUID> — in production UUID::randomUUID, in tests a counter that returns predictable UUIDs. Java's functional interfaces make this a one-liner.

When to use it

  • Any class whose behavior branches on or emits random values.
  • Tests need to verify specific branches or assert on specific outputs.
  • You control the class's construction (direct new or via a DI container you can configure).

When not to use it:

  • Randomness is purely cosmetic — a log correlation ID that no test will ever assert on. Injection is overkill.
  • The random call is deep in a performance-critical loop and the abstraction cost matters — profile first, then decide.

Example

Before — CouponService uses a static random and a raw UUID call:

public class CouponService {
    public Coupon issue(Customer c) {
        UUID id = UUID.randomUUID();
        int discount = ThreadLocalRandom.current().nextInt(5, 26); // 5% – 25%
        boolean premium = ThreadLocalRandom.current().nextDouble() < 0.10;
        return new Coupon(id, c.getId(), discount, premium);
    }
}

Nothing about the returned coupon is predictable. A test asserting "premium should be true about 10% of the time" would require thousands of iterations and would still be flaky.

Steps

  1. List every random-source call: Random, ThreadLocalRandom, Math.random(), UUID.randomUUID(), SecureRandom.
  2. Decide on abstractions. Random itself is often fine as a constructor parameter. For UUIDs, a Supplier<UUID> is cleaner than passing a full generator.
  3. Add constructor parameters, and add a convenience no-arg constructor that supplies the production defaults.
  4. Replace each direct call with a call on the injected source.
  5. In tests, pass new Random(seed) with a known seed, or a small fake that returns pre-programmed values in sequence.

Example (after)

public class CouponService {
    private final Random random;
    private final Supplier<UUID> uuidSource;

    public CouponService(Random random, Supplier<UUID> uuidSource) {
        this.random = random;
        this.uuidSource = uuidSource;
    }

    public CouponService() {
        this(new Random(), UUID::randomUUID);
    }

    public Coupon issue(Customer c) {
        UUID id = uuidSource.get();
        int discount = random.nextInt(5, 26);
        boolean premium = random.nextDouble() < 0.10;
        return new Coupon(id, c.getId(), discount, premium);
    }
}

// Test — same seed, same outputs, every time
@Test
public void issuedCouponUsesInjectedRandomness() {
    Random seeded = new Random(42);
    UUID fakeId = UUID.fromString("00000000-0000-0000-0000-000000000001");

    CouponService svc = new CouponService(seeded, () -> fakeId);
    Coupon c = svc.issue(Customer.withId("cust-1"));

    assertEquals(fakeId, c.getId());
    assertTrue(c.getDiscount() >= 5 && c.getDiscount() < 26);
    // With seed=42, random.nextDouble() returns ~0.73... so premium == false
    assertFalse(c.isPremium());
}

@Test
public void returnsPremiumWhenRandomBelowThreshold() {
    Random scripted = new Random() {
        @Override public int nextInt(int origin, int bound) { return 15; }
        @Override public double nextDouble() { return 0.05; }
    };

    CouponService svc = new CouponService(scripted, () -> UUID.randomUUID());
    Coupon c = svc.issue(Customer.withId("cust-2"));

    assertEquals(15, c.getDiscount());
    assertTrue(c.isPremium());
}

Supporting and alternative techniques

Counter-based UUID sources

Rather than returning the same UUID every time, a test Supplier<UUID> that counts is often more useful — it lets the test distinguish multiple coupons issued in sequence while still being deterministic:

public class CountingUuidSource implements Supplier<UUID> {
    private final AtomicLong counter = new AtomicLong();
    @Override
    public UUID get() {
        return new UUID(0L, counter.incrementAndGet());
    }
}

A narrower interface for finer control

For complex generator logic, inject a domain-specific interface rather than raw Random. CouponService might take a DiscountRoller with methods int discountPercent() and boolean isPremium(). The production implementation consults Random; tests implement the interface directly with whatever values the test needs. This is Extract Interface applied to the random source.

Extract and Override Getter

For classes you can't easily re-wire, fall back to Feathers' standard move: wrap each generator call in a protected method (protected int rollDiscount() { return ThreadLocalRandom.current().nextInt(5, 26); }), then override in a test subclass.

Cautions and variations

Seed choice matters

Tests using new Random(seed) depend on the JDK's PRNG sequence. That sequence is documented and stable across JVM versions — but if you ever switch to a different generator (SplittableRandom, SecureRandom), the sequences differ. For long-term stability, consider scripted fakes rather than seeds.

SecureRandom in production, seeded Random in tests

Production code should usually use SecureRandom for cryptographic purposes. Tests don't need cryptographic strength — a plain seeded Random is fine, because test determinism is the priority. Just make sure the class accepts the base Random type and production passes a SecureRandom.

ThreadLocalRandom and performance

ThreadLocalRandom exists because shared Random instances contend under thread pressure. Injecting a single Random per service can, in extreme cases, become a contention point. Measure before worrying — for most application code, a single instance is fine.

Don't over-inject

A class that already has six constructor parameters doesn't want a seventh for a single random call. If the class is getting crowded, consider a small Randomness holder that bundles the sources it needs, and inject that instead.
