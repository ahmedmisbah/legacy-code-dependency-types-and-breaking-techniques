Hidden Dependency

Java dependency type · Chapter 25 fix: Extract and Override Factory Method

The dependency
Hidden Dependency
The technique
Extract and Override Factory Method

The dependency

A hidden dependency is created when a class's constructor performs non-trivial construction work — branching logic, configuration loading, conditional wiring — that decides which concrete collaborators to use. Unlike a plain constructor dependency (a single new call), a hidden dependency embeds decisions inside construction. Parameterizing the constructor would force every caller to reproduce those decisions, which is often impractical and always ugly.

The classic shape is a constructor that reads configuration, checks environment flags, or tests capabilities, and picks one of several possible collaborators accordingly. The resulting object looks the same from outside, but its internals vary with the environment — and tests inherit whichever variant the environment dictates.

Why this blocks tests

The creation logic isn't a single value to substitute

Parameterize Constructor works when you can replace new Thing() with an incoming parameter. A hidden dependency has an algorithm, not a value. You can't pass in "the result of executing this branching logic under a hypothetical config".

Callers can't reproduce the logic cleanly

Moving the logic into every caller duplicates the decision across the codebase. When the logic later changes (new branch, new config key), every caller needs updating. That's worse, not better.

The chosen collaborator determines behavior

In production, the decision picks the heavy real collaborator (database-backed, network-backed, etc.). In tests, you want a fake — but the decision logic doesn't know about tests and has no way to be told.

Configuration state bleeds into tests

If the decision depends on a config file or environment variable, tests need those set correctly, turning unit tests into integration tests whose outcomes depend on the test environment.

The technique: Extract and Override Factory Method

Extract and Override Factory Method moves the creation logic out of the constructor and into a protected method. The constructor calls the factory method to get its collaborator. Production behavior is unchanged — the factory method still runs the original decision logic. A test subclass overrides the factory method to return whichever fake the test needs, short-circuiting the decision.

This is the technique to reach for whenever parameterizing the constructor would force you to duplicate or encode logic at every call site. It keeps the decision in one place and still gives tests a seam.

When to use it

  • A constructor contains branching or configuration-driven creation logic.
  • The class isn't final and the factory method can be protected.
  • You don't want callers to know anything about how construction decides — the logic is an implementation detail.

When not to use it:

  • The constructor contains a simple new with no decision logic — Parameterize Constructor is simpler.
  • The class is final or the test can't subclass it — use Supersede Instance Variable or restructure the creation logic entirely.

Example

Before — ReportExporter's constructor decides which writer to use based on configuration:

public class ReportExporter {
    private final ReportWriter writer;

    public ReportExporter(Config config) {
        if (config.format() == Format.PDF) {
            writer = new PdfReportWriter(config.outputDir(), config.fontBundle());
        } else if (config.format() == Format.EXCEL) {
            writer = new ExcelReportWriter(config.outputDir(), config.stylesheet());
        } else {
            writer = new CsvReportWriter(config.outputDir());
        }
    }

    public void export(Report report) {
        writer.write(report);
    }
}

Every real writer creates files on disk. Parameterizing the constructor with a ReportWriter would work, but then every production caller has to reproduce the decision logic — or a separate factory class has to exist, which is really the same solution with extra ceremony.

Steps

  1. Identify the creation expression (or block) inside the constructor.
  2. Extract it into a protected method with a descriptive name: createWriter, createGateway, etc.
  3. Have the constructor call the new method and assign the result.
  4. Verify that production behavior is unchanged — the factory method runs the same logic as before.
  5. In tests, create a subclass that overrides the factory method to return a fake. The override should not depend on any subclass-specific state (fields aren't initialized yet when the superclass constructor runs).

Example (after)

public class ReportExporter {
    private final ReportWriter writer;

    public ReportExporter(Config config) {
        this.writer = createWriter(config);
    }

    protected ReportWriter createWriter(Config config) {
        if (config.format() == Format.PDF) {
            return new PdfReportWriter(config.outputDir(), config.fontBundle());
        } else if (config.format() == Format.EXCEL) {
            return new ExcelReportWriter(config.outputDir(), config.stylesheet());
        } else {
            return new CsvReportWriter(config.outputDir());
        }
    }

    public void export(Report report) {
        writer.write(report);
    }
}

// Test subclass — returns a fake without caring about config
class TestableReportExporter extends ReportExporter {
    public TestableReportExporter(Config config) { super(config); }

    @Override
    protected ReportWriter createWriter(Config config) {
        return new FakeReportWriter();
    }
}

@Test
public void exportPassesReportToWriter() {
    FakeReportWriter fake = new FakeReportWriter();
    ReportExporter exporter = new ReportExporter(Config.defaults()) {
        @Override
        protected ReportWriter createWriter(Config c) { return fake; }
    };

    exporter.export(Report.sample());

    assertNotNull(fake.lastWritten);
}
Initialization-order gotcha. The factory method is called from the superclass constructor, which runs before the subclass's own fields are initialized. An override that reads a subclass field will see null. Keep the override self-contained (return a fresh fake inline), use a static holder for configurable fakes, or capture a reference from outside via a final lambda / anonymous inner class that closes over a local.

Supporting and alternative techniques

Parameterize Constructor

If the construction logic turns out to be simpler than it looked — say, just one new guarded by a feature flag — consider moving the decision up a level and parameterizing the constructor to accept the already-constructed collaborator. The flag-checking code becomes the caller's problem, which is often where it belongs anyway.

Extract and Override Getter

When the collaborator isn't constructed in the constructor but lazily on first use, the analogous technique is Extract and Override Getter: move the field access (and lazy init) into a protected getter, and override the getter in a test subclass. The difference is where the decision runs — constructor time (factory method) vs. first-access time (getter). See the pairing page for Instance Variable Dependency.

Cautions and variations

Keep the factory method stateless

The factory method should depend only on its parameters (typically the config object the constructor received). Don't reference instance fields — they may not be initialized yet when the factory runs during construction. Don't cache results in a static field either, unless you explicitly need cross-instance behavior.

Resist calling overrideable methods from constructors in general

Java style guides warn against calling overrideable methods from constructors because of the initialization-order problem. Extract and Override Factory Method is one case where you accept the risk consciously — the override is expected, and you design around the init-order issue. Document the pattern with a comment so the next reader understands why a method is protected and called from the constructor.

Migrate toward constructor injection eventually

Like most Feathers techniques, this is a bridge. Once tests cover the class, consider pushing the decision logic into a separate factory or builder class, and have the constructor simply accept the already-chosen collaborator. The test subclass and the protected method become unnecessary.

Related techniques not covered here. Parameterize Constructor is the primary technique for simpler constructor dependencies — see that pairing page for the standard case. Supersede Instance Variable is the fallback when you can't subclass at all.
