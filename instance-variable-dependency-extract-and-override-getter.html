Instance Variable Dependency

Java dependency type · Chapter 25 fix: Extract and Override Getter

The dependency
Instance Variable Dependency
The technique
Extract and Override Getter

The dependency

An instance variable dependency exists when a class has a field holding a problematic collaborator, and methods inside the class read that field directly. The field may be initialized in the constructor, in a setter, at declaration time, or lazily inside a method. The salient trait is that code inside the class writes this.thing.doSomething() — with direct field access, no indirection, no seam.

This is closely related to constructor dependency but not the same: a constructor dependency concerns how the field is set; an instance variable dependency concerns how the field is used. A class can have its field injected cleanly via a parameterized constructor and still be untestable if some method uses the field through this.field in a way a test can't influence.

Why this blocks tests

Direct field access is unreplaceable

When a method uses this.emailSender.send(...), there's no polymorphism. The call targets whatever instance the field points to. A test can't intervene without either replacing the field value (setter, Parameterize Constructor, Supersede Instance Variable) or intercepting the access itself.

Lazy initialization hides the dependency

A field initialized on first access (inside a getter, inside the method that uses it) is invisible to constructor injection. The class appears to have no collaborator — until the first call to a particular method, at which point the real collaborator springs into existence. Constructor-based techniques miss this case entirely.

Multiple methods use the same field

If five methods all access this.cache, and you want to fake the cache in tests, you need a solution that works for all five. Touching each call site is noisy and error-prone.

Subclassing partially helps, but not for fields

Java lets you override methods in a subclass, but not fields. A test subclass can't simply declare private EmailSender emailSender = new FakeEmailSender(); and have the superclass see it — the superclass sees its own field. The seam has to go through a method.

The technique: Extract and Override Getter

Extract and Override Getter replaces direct field access with calls to a protected getter method. Once every usage routes through the getter, a test subclass can override the getter to return a fake, without touching the field itself. The field remains private; the access path becomes polymorphic.

This technique is particularly useful for the lazy-initialization case: move the lazy-init logic into the getter, and the subclass can supply a value before the lazy-init runs.

When to use it

  • A class has a field holding a problematic collaborator, and multiple methods access it directly.
  • The class isn't final, and a test subclass is feasible.
  • You can't easily rewire construction to inject the dependency (otherwise Parameterize Constructor is cleaner).
  • Lazy initialization is in play and you need to intercept before it runs.

When not to use it:

  • The field is only used in one method — Extract and Override Call around the one use is simpler.
  • You can change the constructor — Parameterize Constructor keeps the design cleaner and avoids subclassing.

Example

Before — WorkflowRunner lazily initializes an email sender and uses it from multiple methods:

public class WorkflowRunner {
    private EmailSender emailSender;

    public void notifyStarted(User user) {
        if (emailSender == null) emailSender = new SmtpEmailSender();
        emailSender.send(user.getEmail(), "Workflow started");
    }

    public void notifyCompleted(User user, Result result) {
        if (emailSender == null) emailSender = new SmtpEmailSender();
        emailSender.send(user.getEmail(), result.summary());
    }
}

There is no place a test can inject a fake. The field goes from null to a real SmtpEmailSender the moment either method is called.

Steps

  1. Identify the field and every place it's read.
  2. Add a protected getter method. Move lazy-initialization logic into the getter.
  3. Replace every direct field read with a call to the getter.
  4. In tests, subclass the class and override the getter to return a fake. The field itself is never accessed.

Example (after)

public class WorkflowRunner {
    private EmailSender emailSender;

    public void notifyStarted(User user) {
        getEmailSender().send(user.getEmail(), "Workflow started");
    }

    public void notifyCompleted(User user, Result result) {
        getEmailSender().send(user.getEmail(), result.summary());
    }

    protected EmailSender getEmailSender() {
        if (emailSender == null) emailSender = new SmtpEmailSender();
        return emailSender;
    }
}

// Test subclass — supplies a fake before lazy init can run
class TestableWorkflowRunner extends WorkflowRunner {
    public FakeEmailSender fake = new FakeEmailSender();
    @Override
    protected EmailSender getEmailSender() { return fake; }
}

@Test
public void notifyStartedSendsMessageToUser() {
    TestableWorkflowRunner runner = new TestableWorkflowRunner();
    runner.notifyStarted(User.withEmail("a@b.com"));

    assertEquals("a@b.com", runner.fake.lastRecipient);
    assertEquals("Workflow started", runner.fake.lastMessage);
}

The real SmtpEmailSender is never constructed — the lazy-init branch inside getEmailSender is dead code as far as the test is concerned, because the override bypasses it.

Supporting and alternative techniques

Supersede Instance Variable

When the class can't be subclassed (or when you don't want to introduce a test subclass), add a test-only setter that replaces the field after construction. The real collaborator is still constructed — you just overwrite it before the test exercises the code.

public class WorkflowRunner {
    private EmailSender emailSender = new SmtpEmailSender();

    // Deliberately ugly name — marks as test-only
    public void supersedeEmailSender(EmailSender replacement) {
        this.emailSender = replacement;
    }

    // ... methods still use the field directly ...
}

Weaker than Extract and Override Getter because the real collaborator is constructed (with whatever side effects that entails), but useful when subclassing isn't available. Feathers considers it a last resort.

Parameterize Constructor

When you can change the constructor, inject the collaborator directly. The class no longer owns its own creation and doesn't need a getter seam at all. This is the design most codebases want to end up at — treat Extract and Override Getter as a stepping-stone toward constructor injection once tests are safe.

public class WorkflowRunner {
    private final EmailSender emailSender;

    public WorkflowRunner(EmailSender emailSender) {
        this.emailSender = emailSender;
    }

    public void notifyStarted(User user) {
        emailSender.send(user.getEmail(), "Workflow started");
    }
}

Cautions and variations

Don't forget lazy init in the getter

If the original code relied on lazy initialization, the getter must preserve it. A getter that returns null the first time is a regression, not a refactoring.

Watch for init order with subclasses

Overriding a getter that's called from a superclass constructor runs before the subclass's fields are initialized. If the subclass stores the fake in a field and the override reads that field, it will be null during construction. Keep the override self-contained, or use a static holder if you need external configurability.

Every read needs to go through the getter

One direct field read that slips through the refactoring is a silent bug waiting to surface. Lean on the compiler: make the field private (if it isn't already) and visible only to the getter. If another method reaches past the getter, the compiler will flag it.

Related techniques not covered here. Extract and Override Factory Method is the variant for classes where the dependency is a collaborator created by the class (inside a constructor or init method) rather than one that's held as a field with lazy init. The two techniques have the same shape — extract to a method, override in a subclass — but serve different init patterns.
