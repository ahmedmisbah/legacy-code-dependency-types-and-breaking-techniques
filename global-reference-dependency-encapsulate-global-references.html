Global Reference Dependency

Java dependency type · Chapter 25 fix: Encapsulate Global References

The dependency
Global Reference Dependency
The technique
Encapsulate Global References

The dependency

A global reference dependency exists when code directly reads from or writes to process-wide state — static fields, environment variables, system properties, the system clock. In Java this looks like System.getenv("DB_URL"), Configuration.INSTANCE.get("timeout"), System.currentTimeMillis(), or a plain public static field that someone is mutating. The reference lives outside the class's object graph, so no constructor argument, no setter, and no subclass override will move it.

Globals are seductive because they dodge the boilerplate of passing values through layers. That convenience is precisely the testability problem: there's no seam at all. Every caller and every test that exercises the class touches the same global, with all the implications that carries.

Why this blocks tests

There is no injection point

Constructor dependencies can be parameterized. Parameter dependencies can be extracted into interfaces. Global references have nowhere to inject — the code asks the JVM itself for the value, and the JVM hands back whatever is there.

Tests leak into each other

If one test sets System.setProperty("mode", "A") and the next reads System.getProperty("mode"), the second test inherits the first one's state. Test order starts mattering. Parallel test execution becomes unsafe. The hard-to-diagnose failures always happen on the CI server and never locally.

You can't observe changes

If the code writes to the global, the test can read it back — but only if the test knows the exact global name. Observing which globals were touched, and in what order, requires intrusive instrumentation.

The dependency is invisible at the API

A class with a plain no-arg constructor and no exotic parameter types looks self-contained, but it secretly needs CONFIG_PATH set, a network-reachable DNS server, and a system clock in UTC. Deploying it to a new environment surfaces each missing global as a runtime failure.

The deeper problem. Globals are a design decision that affects testability, not a testability problem that happens to show up in the design. Encapsulate Global References doesn't eliminate globals; it puts them behind an object so the rest of the code stops noticing.

The technique: Encapsulate Global References

Encapsulate Global References gathers the globals that a class uses into a new class — conventionally named after the role the globals play together (Environment, SystemClock, RuntimeConfig). Accesses to the raw globals become method calls on an instance of that new class. Once the globals are behind an object, every other technique in the catalog becomes available: you can parameterize the constructor to accept the holder, extract an interface from the holder to fake it, subclass it, and so on.

When to use it

  • Code reads or writes System.*, Environment.*, or static fields of shared configuration classes.
  • The globals form a natural group (all about time, all about environment, all about configuration) — the wrapper's name writes itself.
  • Multiple classes touch the same globals — one encapsulation benefits all of them.

When not to use it:

  • The global is a true singleton-style service (getInstance()) — use Introduce Static Setter instead.
  • A single method uses a single global value — Parameterize Method is simpler.

Example

Before — PricingService reads environment variables, system properties, and the clock directly:

public class PricingService {
    public Money finalPrice(Order order) {
        double taxRate = Double.parseDouble(System.getenv("TAX_RATE"));
        boolean isHoliday = Boolean.parseBoolean(System.getProperty("holiday.mode"));
        Instant now = Instant.now();

        Money base = order.subtotal();
        if (isHoliday && now.atZone(ZoneOffset.UTC).getMonth() == Month.DECEMBER) {
            base = base.times(0.90);
        }
        return base.plus(base.times(taxRate));
    }
}

Testing this means setting and unsetting environment variables (which Java makes deliberately awkward), setting and clearing system properties, and having the test run at a specific time of year. Every test becomes a fight with the JVM's global state.

Steps

  1. List every global reference the class uses. Group them by role (environment config, clock, runtime flags).
  2. Create a new class named after the role. Give it methods that return the values, initially just delegating to the same globals.
  3. Add a field in the original class that holds an instance of the new class. Default-initialize it to a real instance.
  4. Replace every direct global access in the original class with a call on the new field.
  5. Apply Parameterize Constructor so tests can inject a different instance.
  6. Optionally, extract an interface from the holder and accept the interface instead of the concrete class.

Example (after)

// The wrapper — still consults the real globals by default
public class Environment {
    public double taxRate() {
        return Double.parseDouble(System.getenv("TAX_RATE"));
    }
    public boolean holidayMode() {
        return Boolean.parseBoolean(System.getProperty("holiday.mode"));
    }
    public Instant now() {
        return Instant.now();
    }
}

public class PricingService {
    private final Environment env;

    public PricingService(Environment env) {
        this.env = env;
    }

    public PricingService() { this(new Environment()); }

    public Money finalPrice(Order order) {
        Money base = order.subtotal();
        if (env.holidayMode() && env.now().atZone(ZoneOffset.UTC).getMonth() == Month.DECEMBER) {
            base = base.times(0.90);
        }
        return base.plus(base.times(env.taxRate()));
    }
}

// Test — no environment variables, no system properties, no wall clock
public class FakeEnvironment extends Environment {
    public double tax = 0.1;
    public boolean holiday = false;
    public Instant time = Instant.parse("2026-06-15T00:00:00Z");

    @Override public double taxRate() { return tax; }
    @Override public boolean holidayMode() { return holiday; }
    @Override public Instant now() { return time; }
}

@Test
public void holidayDiscountOnlyAppliesInDecember() {
    FakeEnvironment env = new FakeEnvironment();
    env.holiday = true;
    env.time = Instant.parse("2026-06-15T00:00:00Z");

    PricingService svc = new PricingService(env);
    Money total = svc.finalPrice(Order.of(Money.usd(100)));

    assertEquals(Money.usd(110), total); // no holiday discount outside Dec
}

Supporting and alternative techniques

Replace Global Reference with Getter

A lighter-touch alternative. Instead of extracting a separate wrapper class, introduce a protected getter inside the same class that returns the global value. Subclass the class in tests and override the getter.

Before — direct global access:

public class PricingService {
    public Money finalPrice(Order order) {
        double taxRate = Double.parseDouble(System.getenv("TAX_RATE"));
        return order.subtotal().plus(order.subtotal().times(taxRate));
    }
}

After — access via an overridable getter:

public class PricingService {
    public Money finalPrice(Order order) {
        return order.subtotal().plus(order.subtotal().times(getTaxRate()));
    }

    protected double getTaxRate() {
        return Double.parseDouble(System.getenv("TAX_RATE"));
    }
}

// Test subclass
class TestablePricingService extends PricingService {
    @Override protected double getTaxRate() { return 0.1; }
}

This is quicker than full encapsulation, but it spreads the workaround across every class that uses the global instead of consolidating in one place. Prefer Encapsulate Global References when multiple classes touch the same globals.

Parameterize Method

If a single method uses a single global, and the calling context already knows the value, the simplest fix is to pass it in as an argument. No wrapper class, no subclass — just an extra parameter.

// Before
public Money finalPrice(Order order) {
    double taxRate = Double.parseDouble(System.getenv("TAX_RATE"));
    return order.subtotal().times(1 + taxRate);
}

// After
public Money finalPrice(Order order, double taxRate) {
    return order.subtotal().times(1 + taxRate);
}

Cautions and variations

Don't just rename the problem

A wrapper whose methods simply call the same globals buys nothing if you never vary the wrapper. The point of encapsulation is to make substitution possible — pair with Parameterize Constructor and an interface (or a subclass override) or the exercise was decorative.

Group by cohesion, not by expedience

Stuffing every global your class uses into one Globals class produces a grab-bag that's hard to fake. Split by role: a Clock wrapper for time, a ConfigSource wrapper for configuration, an Environment wrapper for process info. Each narrow wrapper can be faked independently in the tests that need it.

Java's standard Clock

For the specific case of time, don't roll your own wrapper — java.time.Clock already exists, is injectable, and has test utilities built in (Clock.fixed, Clock.offset). Use it as the model for other Encapsulate Global References applications.

Related techniques not covered here. Introduce Static Setter addresses a closely related problem — a globally accessible object reached through getInstance() — by adding a static setter for tests. Use it when the global is a service object, rather than a raw value.
