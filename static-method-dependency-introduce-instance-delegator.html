Static Method Dependency

Java dependency type · Chapter 25 fix: Introduce Instance Delegator

The dependency

A static method dependency happens when the code under test calls a static method on another class directly: TaxTables.lookupRate(state), Logging.log(msg), FileUtils.readText(path). The call is resolved at compile time against a specific class — there is no object in between, no polymorphism, no virtual dispatch. Tests have nowhere to intervene.

Static calls are a special case of global reference dependency, but they deserve their own treatment because the fix is different. A global reference is usually a value you can wrap; a static call is a behavior that you want to substitute. The technique for behavior is to give the call an object seam.

Why this blocks tests

Static calls can't be polymorphically replaced

In Java, a call like TaxTables.lookupRate(state) is bound at compile time to exactly that class's method. You can't override it through inheritance; you can't substitute a different implementation through an interface. Every run of the code executes the same code path.

Mocking frameworks generally can't help

Mockito, by default, can't mock static methods. Tools that can (PowerMock, Mockito's mockStatic) work by manipulating the classloader or bytecode, which is slow, fragile, and confusing. When tests use heavyweight mocking tricks to paper over design problems, the design usually gets worse, not better.

The call site is a dead end

There's no parameter to swap, no field to replace, no constructor to parameterize. The static call is baked into the method body, and tests of that method inherit whatever the static does — including real I/O, real database reads, or real external API calls.

Error paths become unreachable

If the static method throws on certain inputs, the only way to exercise that error path is to produce those inputs. If it reads from the filesystem, the test has to arrange specific files. The combinatorial cost of covering failure modes spirals.

The technique: Introduce Instance Delegator

Introduce Instance Delegator creates an object seam around a static call. You add an instance method — either on the class under test itself or on a new helper class — that delegates to the static method. The production code path is unchanged (the delegator still calls the static). In tests, a subclass or a fake helper overrides the delegator method and returns whatever the test needs.

The technique doesn't remove the static method, and it doesn't fix the fundamental design issue of a utility class full of statics. What it does is turn one specific static call site into an object call, at which point every other technique in the catalog becomes available.

When to use it

  • Code under test calls a static method whose behavior you need to vary in tests.
  • You own the class under test (you can add a new instance method to it) or you own a helper class you can route calls through.
  • You want a minimal change — this technique adds one method without restructuring the caller.

When not to use it:

  • The static method's logic is simple and self-contained — Expose Static Method might let you test the logic directly without routing through an instance.
  • The value returned by the static is already computed elsewhere and could be passed in — Parameterize Method is simpler.

Example

Before — InvoiceCalculator calls TaxTables.lookupRate statically:

public class TaxTables {
    public static BigDecimal lookupRate(String state) {
        // reads a configuration file from disk, caches, etc.
        return loadFromFile(state);
    }
}

public class InvoiceCalculator {
    public BigDecimal totalWithTax(Order order) {
        BigDecimal rate = TaxTables.lookupRate(order.getState());
        return order.subtotal().multiply(BigDecimal.ONE.add(rate));
    }
}

Testing totalWithTax requires a real configuration file reachable from the test runner, with the specific tax rates the test expects.

Steps

  1. Identify the static method call you want to neutralize.
  2. Add a protected instance method on the class under test. Give it the same signature as the static but make it an instance method. Its body is a single line delegating to the static.
  3. Replace the static call in the method body with a call to the new instance method.
  4. In tests, subclass the class under test and override the delegator method to return canned values.

Example (after)

public class InvoiceCalculator {
    public BigDecimal totalWithTax(Order order) {
        BigDecimal rate = lookupRate(order.getState());
        return order.subtotal().multiply(BigDecimal.ONE.add(rate));
    }

    // The delegator: production still calls the static;
    // tests override this method to return canned rates.
    protected BigDecimal lookupRate(String state) {
        return TaxTables.lookupRate(state);
    }
}

// Test subclass
class TestableInvoiceCalculator extends InvoiceCalculator {
    public String lookedUpState;

    @Override
    protected BigDecimal lookupRate(String state) {
        lookedUpState = state;
        return new BigDecimal("0.10");
    }
}

@Test
public void totalWithTaxAppliesStateRate() {
    TestableInvoiceCalculator calc = new TestableInvoiceCalculator();
    Order order = Order.of(Money.usd(100), "CA");

    BigDecimal result = calc.totalWithTax(order);

    assertEquals("CA", calc.lookedUpState);
    assertEquals(new BigDecimal("110.00"), result);
}

No files are read. No tax tables are consulted. The test is deterministic, fast, and isolated.

Supporting and alternative techniques

Expose Static Method

When the logic inside the static method doesn't depend on its class's state (no private fields accessed), you can sometimes test the static directly rather than working around it. Feathers' Expose Static Method technique flips the problem: instead of wrapping the static call in an instance method, extract the static's body into a separate static that takes everything it needs as parameters, then test that directly.

This applies when you're the author of both the caller and the called static, and you realise the static is doing pure computation that just happened to be stuck on a utility class. After applying the technique, you can test the extracted piece in isolation without any delegator at all.

Parameterize Method

If the value computed by the static is already known (or easily computed) at the call site of the method under test, don't bother with a delegator — just pass the value in as a parameter. This is the simplest possible fix and should always be considered first for one-off situations.

// Before
public BigDecimal totalWithTax(Order order) {
    BigDecimal rate = TaxTables.lookupRate(order.getState());
    return order.subtotal().multiply(BigDecimal.ONE.add(rate));
}

// After — caller passes the rate in
public BigDecimal totalWithTax(Order order, BigDecimal rate) {
    return order.subtotal().multiply(BigDecimal.ONE.add(rate));
}

This pushes the static call up one level (the caller still has to make it), so the problem doesn't disappear — it migrates. That can be a win if the caller has better options for replacing the static.

Cautions and variations

Don't over-proliferate delegators

If a class has ten static calls, wrapping each in its own delegator method clutters the class. At that point, consider a different strategy: create a new helper class (sometimes called a seam class or gateway) that owns all the static calls as instance methods. Inject the helper through the constructor and call it instead of the statics. This is effectively Encapsulate Global References applied to behavior.

The static is still there

Like most Feathers techniques, Introduce Instance Delegator buys you a test seam without fixing the underlying problem. Once tests cover the class, consider eliminating the static entirely: convert the utility to an interface and inject an implementation.

Don't mock the delegator with a library

The delegator is designed for plain subclassing and method override. Using Mockito to stub it works but obscures the intent — a reader seeing the test sees Mockito magic, not a simple override. Prefer a hand-written test subclass unless there's a strong reason otherwise.

Related techniques not covered here. For singletons (static accessors to a shared object, rather than static methods performing a computation), use Introduce Static Setter. For raw globals (static fields, environment variables), use Encapsulate Global References.
