DI Container Dependency

Java dependency type · Modern Java technique: Bypass the Container

Bypass the Container
Not in Chapter 25. Feathers' book was published in April 2004 — the same year Spring reached its 1.0 release, and three years before Guice. DI containers as a dominant Java pattern were still on the horizon. The dependency type this page describes — a class that can only be instantiated by the container — didn't exist widely enough to name. The fix, though, is pure Feathers: apply Parameterize Constructor rigorously, so the container is no longer load-bearing for tests.

The dependency

A DI container dependency exists when a class is structured in a way that assumes a dependency-injection framework (Spring, Guice, CDI, Dagger) will do the wiring. The class uses @Autowired on fields, requires the container to resolve @PostConstruct hooks, relies on container-managed proxies for @Transactional or @Async behavior, or receives configuration through @Value annotations with no constructor path. Tests that want to exercise the class have to stand up the container itself — often the full application context — to get anything done.

The problem isn't the container; containers are genuinely useful for production wiring. The problem is that the class's design has become container-coupled — the container isn't an optional wiring convenience, it's a structural prerequisite. Once that's true, the fast feedback loop of unit testing is replaced by the slow feedback loop of integration testing.

Why this blocks tests

Container startup is seconds, not milliseconds

Booting a Spring application context — even a minimal slice — takes several seconds: classpath scanning, bean definition parsing, proxy generation, lifecycle hooks. A test suite of five hundred "unit" tests that each boot a context spends most of its time in startup. TDD's rapid red-green loop collapses into a wait-and-check ritual.

One test instantiates a graph of beans

A class with three @Autowired dependencies, each of which has its own dependencies, can't be constructed in isolation. The container tries to satisfy the whole graph. Even with @MockBean to short-circuit pieces, the test is effectively integration-testing the container's wiring logic alongside the class's own behavior.

Field injection hides the contract

A class with @Autowired private UserRepository repo and no matching constructor tells callers nothing about what it needs. Discovering the real dependencies requires reading the source, not the signature. Tests can't supply alternatives without reflection tricks or dedicated test frameworks.

@PostConstruct and proxy magic

Lifecycle annotations run automatically when the container instantiates a bean. A test that constructs the class with new skips those hooks and gets a partially-initialized object. Similarly, AOP proxies (for @Transactional, @Async, @Cacheable) are created by the container — calling the class directly bypasses them, which may make tests behave differently from production.

Test doubles require the container too

@MockBean and @TestConfiguration only work when the container is running. That couples the test to the framework at yet another layer. Swapping Spring for a different DI tool would rewrite not just production wiring but the entire test suite.

The technique: Bypass the Container

Bypass the Container is a design discipline, applied mechanically: every dependency of the class becomes a constructor parameter. No @Autowired on fields, no setter injection, no @Value without a constructor path. The container still wires production — modern Spring does constructor-parameter autowiring without any annotations on the constructor — but the class's structure no longer depends on the container. Tests construct the class with new, pass fakes, and exercise behavior without booting anything.

The class's public shape now says what it needs. Its tests say so too. The container becomes what it was supposed to be: a convenient production-wiring tool, not a framework requirement.

When to use it

  • A class uses field injection, setter injection, or container-managed lifecycle hooks.
  • Tests of the class require booting the DI container.
  • You can modify the class to take its dependencies through a constructor.

When not to use it:

  • The class genuinely exists only for container-managed behavior — a @Configuration class, a @Component that's really just a bean-definition holder. Test these at integration level, not unit level.
  • The class relies on container proxies (@Transactional, @Async) that are the point of the class's existence. Test the non-proxied logic as a unit and write a small integration test for the proxy behavior.

Example

Before — UserService uses field injection throughout:

@Service
public class UserService {
    @Autowired private UserRepository repo;
    @Autowired private EmailService email;
    @Autowired private AuditLogger audit;
    @Value("${welcome.subject}") private String welcomeSubject;

    @PostConstruct
    public void init() { audit.record("UserService ready"); }

    public User register(String name, String emailAddress) {
        if (repo.findByEmail(emailAddress).isPresent()) {
            throw new UserAlreadyExistsException();
        }
        User user = repo.save(new User(name, emailAddress));
        email.send(emailAddress, welcomeSubject, "Welcome, " + name);
        audit.record("registered:" + user.getId());
        return user;
    }
}

Testing register requires a Spring context — or reflection hacks to set the private fields. @SpringBootTest works but boots the whole application; @MockBean helps but ties the test to the framework. Either way, the test is slow and structurally coupled to Spring.

Steps

  1. Remove @Autowired from fields. Make each field private final.
  2. Remove @Value from fields. Each configuration value becomes a constructor parameter (typed as String, int, or a small value object).
  3. Add a single constructor taking all dependencies and configuration values. Modern Spring auto-wires a single public constructor without needing @Autowired.
  4. Replace @PostConstruct logic either by moving it into the constructor (if simple) or by keeping the annotation and acknowledging that unit tests won't trigger it (and aren't meant to — test it separately if it matters).
  5. Verify production still wires up — usually no extra work if Spring is recent (5.x+).
  6. Write tests that construct the class with new and pass hand-written fakes.

Example (after)

@Service
public class UserService {
    private final UserRepository repo;
    private final EmailService email;
    private final AuditLogger audit;
    private final String welcomeSubject;

    public UserService(UserRepository repo,
                       EmailService email,
                       AuditLogger audit,
                       @Value("${welcome.subject}") String welcomeSubject) {
        this.repo = repo;
        this.email = email;
        this.audit = audit;
        this.welcomeSubject = welcomeSubject;
    }

    public User register(String name, String emailAddress) {
        if (repo.findByEmail(emailAddress).isPresent()) {
            throw new UserAlreadyExistsException();
        }
        User user = repo.save(new User(name, emailAddress));
        email.send(emailAddress, welcomeSubject, "Welcome, " + name);
        audit.record("registered:" + user.getId());
        return user;
    }
}

// Test — no Spring, no container, millisecond runtime
@Test
public void registerCreatesUserAndSendsWelcome() {
    FakeUserRepository repo = new FakeUserRepository();
    FakeEmailService email = new FakeEmailService();
    FakeAuditLogger audit = new FakeAuditLogger();

    UserService svc = new UserService(repo, email, audit, "Welcome!");
    User user = svc.register("Alice", "a@b.com");

    assertEquals("Alice", user.getName());
    assertEquals("a@b.com", email.lastRecipient);
    assertEquals("Welcome!", email.lastSubject);
    assertTrue(audit.lastEntry.startsWith("registered:"));
}

@Test
public void registerRejectsDuplicateEmail() {
    FakeUserRepository repo = new FakeUserRepository();
    repo.save(new User("Existing", "a@b.com"));

    UserService svc = new UserService(repo, new FakeEmailService(),
                                         new FakeAuditLogger(), "Welcome!");

    assertThrows(UserAlreadyExistsException.class,
        () -> svc.register("Alice", "a@b.com"));
}

Spring still works in production — it sees the single constructor and autowires each parameter against the bean graph, and the @Value placeholder still resolves. Tests no longer need any of that.

Supporting and alternative techniques

Parameterize Constructor (the Ch 25 root)

This entire page is an application of Feathers' Parameterize Constructor technique to the specific case of container-managed classes. The only thing new is recognizing that DI containers can inadvertently push codebases away from Parameterize Constructor (by making field injection look equally convenient), and that dragging them back is a small act of discipline.

Separate proxy-dependent behavior into a wrapper

If a method genuinely needs @Transactional or @Async proxy behavior that only the container can provide, split the class: the core logic goes into a class with plain methods (fully unit-testable), and a thin wrapper applies the annotation. The wrapper is tested as a small integration test; the core is tested as a normal unit.

Constructor-based integration tests when needed

Some behavior only emerges from the wired-up application: transaction boundaries, security filters, autoconfiguration. Keep a small number of integration tests for these — but keep them a minority. Most classes should have plain unit tests with constructor-injected fakes, and a few focused integration tests verify the container actually wires everything correctly.

Cautions and variations

Many-parameter constructors are a smell

If removing field injection leaves you with a constructor taking nine parameters, the class has too many responsibilities — the container was hiding the coupling. Fix by splitting: multiple smaller classes, each with fewer parameters. The refactor is driven by the discomfort of the parameter count, which is the point.

@Value at the constructor works, but prefer typed objects

Taking @Value("${port}") int port in a constructor is fine for isolated configuration. Once the class takes more than two configuration values, consider a typed @ConfigurationProperties object instead — the class receives a small properties bean rather than a grab bag of primitives. Tests construct the bean directly.

Don't disable the container — replace it in tests

The goal isn't to avoid Spring/Guice — they're fine in production. The goal is to make tests not require them. Production can still use all the container's features. Tests construct the class directly and pass fakes, because they can.

Migrating field-injected code takes time

A legacy codebase with thousands of @Autowired field injections is a lot of work to migrate. The rewrite is mechanical (IDE tools help), but it's also tedious and touches many files. Do it incrementally — when you'd touch a class anyway for a feature, convert its injection style at the same time. Greenfield code uses constructor injection from the start.
