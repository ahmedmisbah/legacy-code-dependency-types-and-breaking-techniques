Inheritance Dependency

Java dependency type · Modern Java technique: Compose Around the Inherited Type

Not in Chapter 25. Feathers' Pull Up Feature technique addresses a different shape: pull testable logic up into a parent class you own. That doesn't help when the forced parent is a framework class (HttpServlet, AbstractPageBean, a Spring ViewController, a JPA Repository base) — you can't modify the parent, so there's no "up" to pull anything to. The modern Java pattern inverts the move: the framework-extending class becomes a thin shell that delegates to a plain class of your own, which is what gets tested.

The dependency

An inheritance dependency exists when a class is forced to extend a parent you don't control — a servlet base class, a framework lifecycle hook, an ORM entity superclass, a Spring WebSecurityConfigurerAdapter, a test-framework base class. The parent dictates construction, protected API surface, and often runtime lifecycle. Your class inherits all of that whether it wants to or not.

The testability problem is that any test of the class runs through the parent. Instantiation invokes the parent's constructor (which may require a framework context). Methods you care about are often called by the framework, not by callers in your code, so you can't exercise them in isolation. And the interesting business logic is inevitably tangled with framework calls (getSession(), getRequest(), persist()) that pull in even more of the framework.

Why this blocks tests

You can't construct the class in isolation

A HttpServlet subclass works when the servlet container has done init. A JPA entity behaves correctly when the EntityManager is around. A Spring controller relies on the request-scoped beans. new YourClass() in a test produces an object the framework never sees — and the framework's absent contributions show up as nulls and surprise exceptions.

Protected methods mean tests reach through the API

Framework parents typically expose hooks as protected methods (doGet, onEvent, process). In production the framework calls them; in tests you either subclass to expose them or call them via reflection. Either way, the test is picking at the internal shape of the class rather than exercising its purpose.

Business logic and framework logic are fused

Inside a doPost that validates a form and saves an order, the form-reading code knows HttpServletRequest, the validation code doesn't, and the saving code knows the database. They're all in one method because the framework forced them into the same class. There's no seam to isolate the validation by itself.

Single inheritance forecloses other options

Java permits only one superclass. If framework X requires you to extend FrameworkXBase, you can't also extend a class you wrote. Mixing framework inheritance with your own inheritance-based design is impossible — you have to choose, and the framework typically wins.

The technique: Compose Around the Inherited Type

Compose Around the Inherited Type shrinks the framework-extending class to the minimum: it extracts request data, calls a plain handler class you own, and writes the response. The handler class has no framework parent, no framework types in its signatures, and receives everything it needs as plain arguments. It's a normal Java class — testable with new, no container required.

This is sometimes called the "Humble Object" pattern: the framework-coupled part becomes a humble translator with almost no logic, and all the logic moves into a companion class that knows nothing about the framework. The testable surface is the companion; the framework class exists only to host the translation.

When to use it

  • Your class extends a framework base class you don't own.
  • The class contains real business logic that deserves unit tests.
  • You can introduce a new class and wire it into the framework-extending class.

When not to use it:

  • The class is almost entirely framework plumbing with one line of interesting logic — extract the one line, don't build a whole handler for it.
  • The class genuinely exists to implement a framework contract (say, a custom ViewResolver) whose whole purpose is the framework behavior. Test it with framework-level integration tests.

Example

Before — OrderServlet extends HttpServlet and mixes form parsing, validation, and order submission:

public class OrderServlet extends HttpServlet {
    private final OrderRepository orders;
    private final PriceService pricing;

    public OrderServlet(OrderRepository orders, PriceService pricing) {
        this.orders = orders;
        this.pricing = pricing;
    }

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String sku = req.getParameter("sku");
        String qtyRaw = req.getParameter("qty");
        String customerId = req.getParameter("customer");

        if (sku == null || qtyRaw == null) {
            resp.sendError(400, "missing parameters");
            return;
        }

        int qty = Integer.parseInt(qtyRaw);
        if (qty <= 0) {
            resp.sendError(400, "invalid quantity");
            return;
        }

        Money unitPrice = pricing.lookup(sku);
        Order order = new Order(customerId, sku, qty, unitPrice.times(qty));
        orders.save(order);

        resp.setStatus(201);
        resp.getWriter().write("{\"id\":\"" + order.getId() + "\"}");
    }
}

Testing the validation (missing parameters, negative quantity) requires a HttpServletRequest and HttpServletResponse. Mocking both is noisy. Running a real servlet container is worse. And the actual order-submission logic — the part worth testing — is wedged between I/O concerns you can't easily separate.

Steps

  1. Identify the business logic that isn't inherently framework-coupled (validation rules, order construction, price calculation — not HTTP status codes or response bodies).
  2. Create a new handler class taking plain Java arguments and returning a plain Java result (or throwing a plain Java exception).
  3. Move the business logic into the handler. Replace framework calls with parameters or fields on the handler.
  4. Shrink the framework-extending class to: parse framework input into handler arguments, call the handler, translate the handler's result into framework output.
  5. Test the handler directly with new. Framework-level tests cover the thin translator if needed.

Example (after)

// The handler — plain Java, no framework parent
public class OrderSubmissionHandler {
    private final OrderRepository orders;
    private final PriceService pricing;

    public OrderSubmissionHandler(OrderRepository orders, PriceService pricing) {
        this.orders = orders;
        this.pricing = pricing;
    }

    public Order submit(OrderRequest request) {
        if (request.sku() == null) throw new MissingParameterException("sku");
        if (request.qty() <= 0) throw new InvalidQuantityException(request.qty());

        Money unitPrice = pricing.lookup(request.sku());
        Order order = new Order(request.customerId(), request.sku(), request.qty(),
                                  unitPrice.times(request.qty()));
        orders.save(order);
        return order;
    }
}

// Small record for handler input (Java 14+ syntax shown)
public record OrderRequest(String customerId, String sku, int qty) {}

// The servlet — now a thin translator
public class OrderServlet extends HttpServlet {
    private final OrderSubmissionHandler handler;

    public OrderServlet(OrderSubmissionHandler handler) { this.handler = handler; }

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        try {
            OrderRequest r = new OrderRequest(
                req.getParameter("customer"),
                req.getParameter("sku"),
                parseQty(req.getParameter("qty")));
            Order order = handler.submit(r);
            resp.setStatus(201);
            resp.getWriter().write("{\"id\":\"" + order.getId() + "\"}");
        } catch (MissingParameterException | InvalidQuantityException e) {
            resp.sendError(400, e.getMessage());
        }
    }

    private static int parseQty(String raw) {
        if (raw == null) throw new MissingParameterException("qty");
        return Integer.parseInt(raw);
    }
}

// Tests — no servlet container, no framework at all
@Test
public void rejectsNegativeQuantity() {
    OrderSubmissionHandler h = new OrderSubmissionHandler(
        new InMemoryOrderRepository(), PriceService.flat(Money.usd(10)));

    assertThrows(InvalidQuantityException.class,
        () -> h.submit(new OrderRequest("cust-1", "SKU-1", -3)));
}

@Test
public void savesOrderWithCalculatedTotal() {
    InMemoryOrderRepository repo = new InMemoryOrderRepository();
    OrderSubmissionHandler h = new OrderSubmissionHandler(repo, PriceService.flat(Money.usd(10)));

    Order order = h.submit(new OrderRequest("cust-1", "SKU-1", 3));

    assertEquals(Money.usd(30), order.getTotal());
    assertSame(order, repo.findById(order.getId()));
}

The handler has no HttpServletRequest, no response, no framework init. The servlet is a ten-line translator whose only interesting behavior is mapping exception types to HTTP statuses — if that mapping grows complex, it becomes a small tested function on its own. Framework-level integration tests verify the servlet/handler wiring, but the business logic has a fast, focused unit-test surface.

Supporting and alternative techniques

Extract Interface on the handler

Once the handler exists, you can extract an interface from it if multiple implementations make sense (real handler, feature-flagged handler, logging handler). The servlet depends on the interface, not the concrete class. This is straight Extract Interface from Ch 25 applied to the newly-extracted handler.

Keep the translator boring

Every line of logic you leave in the servlet is a line you can't unit-test cheaply. If you find yourself adding if statements, format-detection, or retry loops to the servlet, those almost certainly want to be on the handler side. The discipline is: the servlet does framework-shaped translation, and nothing else.

Parameterize Constructor

The handler is wired into the servlet via constructor injection. Framework-specific instantiation (Spring's @Autowired, CDI's @Inject, ServletConfig.getInitParameter) is done in the framework-extending class; the handler receives plain dependencies. Same principle as the DI Container Dependency page applied at a different level.

Cautions and variations

Don't duplicate the framework's job

If your handler accepts a Map<String,String> of parameters and starts doing HTTP-specific parsing (checking content types, decoding URLs), you've rebuilt a servlet inside your handler. Let the framework do framework things; the handler takes already-parsed, already-typed arguments.

Framework-lifecycle logic stays on the framework side

Methods like init, destroy, @PostConstruct handle framework lifecycle. They belong in the framework-extending class. If they contain business logic (eager cache loading, for instance), extract that logic into a method the handler can call, and have the lifecycle hook call into the handler.

One handler per endpoint is usually right

A servlet that serves five related HTTP endpoints can delegate to five handlers (or one handler with five methods, depending on cohesion). Resist the urge to build a single GenericHandler that takes an operation name — that's rebuilding a router in miniature.

Integration tests still earn their place

Unit tests cover the handler's logic. A small number of integration tests cover the servlet's translation: that missing parameters produce 400, that a successful submission returns 201 with a JSON body, that the right MIME types are set. Those integration tests are few and fast because they don't test anything the handler tests already cover.
