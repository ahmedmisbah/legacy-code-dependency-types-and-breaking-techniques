Large-Class Dependency

Java dependency type · Chapter 25 fix: Push Down Dependency

The dependency
Large-Class Dependency
The technique
Push Down Dependency

The dependency

A large-class dependency isn't a single bad field or a single bad call — it's the cumulative weight of many. The class has become so big and so entangled that every individual dependency-breaking technique, applied on its own, doesn't move the needle. Parameterize Constructor fixes one field, but the class has twelve. Extract and Override Call fixes one side effect, but the class has dozens. Extract Interface on each collaborator produces a wall of interfaces no one wants to maintain.

Feathers' answer isn't "break everything one at a time." It's to make the class itself testable in two versions: a production version that wires in all the heavy real dependencies, and a test-friendly version that doesn't. Push Down Dependency is the mechanical move that separates the two.

Why this blocks tests

The class can't be constructed without its ecosystem

A class with a database client, an LDAP connection, a mail sender, a message queue, a metrics emitter, a cache, and a job scheduler all as direct collaborators needs every one of them to exist before it will instantiate. Setting up tests means setting up production.

Fixing one dependency at a time doesn't help enough

If you apply Parameterize Constructor to one field, the constructor now takes twelve parameters instead of eleven — and you still can't test anything because the other eleven are still real. Incremental dependency breaking only helps when you're most of the way done.

Subclassing to override methods doesn't scale

Extract and Override Getter, Extract and Override Call, and their relatives each add one seam per problem. On a class with dozens of problems, the result is a test subclass overriding thirty methods — unreadable, fragile, and still brittle.

The class mixes concerns at multiple levels

Often the large class has genuine business logic (worth testing) intertwined with infrastructure wiring (not worth testing in unit tests). You want the logic without the wiring. Splitting them by hand is a large refactor; pushing the wiring down one level is a smaller, safer move that enables the same tests.

The technique: Push Down Dependency

Push Down Dependency keeps the original class's interface intact but makes it abstract. A new concrete subclass (conventionally named for the production environment: Production<X>, Real<X>) takes ownership of the problematic dependencies — the fields, their construction, and any methods that touch them. The abstract base class keeps the business logic; the subclass holds the infrastructure glue.

Tests run against a different subclass — typically a hand-written test double that provides trivial implementations of the abstract methods (returning canned values, recording calls). The abstract base class gets exercised through both subclasses, but only the test subclass is ever instantiated during unit tests.

When to use it

  • A class has many problematic dependencies, not just one or two.
  • The business logic can be articulated in terms of a handful of abstract operations (findUser, sendNotification, recordAudit) even if each operation currently involves a real collaborator.
  • You're willing to create a subclass and route production instantiation through it.
  • You can't easily split the class into several smaller classes (that's the better long-term fix, but often much more work).

When not to use it:

  • Only one or two dependencies are causing trouble — address them individually.
  • The class can be safely split into smaller, focused classes — do that instead. Push Down Dependency creates inheritance depth, which has its own costs.

Example

Before — UserAccountManager has a database, an LDAP client, and a mail service all wired into it directly:

public class UserAccountManager {
    private final DatabaseClient db;
    private final LdapClient ldap;
    private final MailService mail;
    private final AuditLog audit;

    public UserAccountManager() {
        this.db = new DatabaseClient(Config.dbUrl());
        this.ldap = new LdapClient(Config.ldapUrl());
        this.mail = new SmtpMailService();
        this.audit = new AuditLog();
    }

    public AccountResult provision(String username, String email) {
        if (db.findUser(username) != null) return AccountResult.exists();
        if (!ldap.hasRole(username, "eligible")) return AccountResult.denied();

        User user = db.createUser(username, email);
        mail.send(email, "Welcome, " + username);
        audit.record("provisioned:" + username);
        return AccountResult.ok(user);
    }
}

There's actual business logic in provision — the uniqueness check, the eligibility rule, the sequence of steps. But exercising it means constructing a DatabaseClient, LdapClient, SmtpMailService, and AuditLog. Each has its own dependencies. The test setup is bigger than the production code.

Steps

  1. Identify which operations in the class are "infrastructure wrappers" — a call to db.findUser, a call to mail.send, etc. Each will become an abstract method.
  2. Declare the original class abstract and replace each infrastructure call with a call to a new abstract method of similar name.
  3. Remove the problematic fields from the base class. The base now knows nothing about DatabaseClient or LdapClient directly.
  4. Create a concrete subclass named for production (ProductionUserAccountManager). It holds the problematic fields, constructs them, and implements each abstract method by delegating to the real collaborator.
  5. Update production instantiation sites to use the new subclass name.
  6. In tests, subclass the base class with a test-only subclass whose abstract method implementations return canned data and record calls.

Example (after)

public abstract class UserAccountManager {

    public AccountResult provision(String username, String email) {
        if (findUser(username) != null) return AccountResult.exists();
        if (!hasEligibleRole(username)) return AccountResult.denied();

        User user = createUser(username, email);
        sendWelcome(email, username);
        recordAudit("provisioned:" + username);
        return AccountResult.ok(user);
    }

    protected abstract User findUser(String username);
    protected abstract boolean hasEligibleRole(String username);
    protected abstract User createUser(String username, String email);
    protected abstract void sendWelcome(String email, String username);
    protected abstract void recordAudit(String entry);
}

// Production wiring — infrastructure lives here, not in the base class
public class ProductionUserAccountManager extends UserAccountManager {
    private final DatabaseClient db = new DatabaseClient(Config.dbUrl());
    private final LdapClient ldap = new LdapClient(Config.ldapUrl());
    private final MailService mail = new SmtpMailService();
    private final AuditLog audit = new AuditLog();

    @Override protected User findUser(String u) { return db.findUser(u); }
    @Override protected boolean hasEligibleRole(String u) { return ldap.hasRole(u, "eligible"); }
    @Override protected User createUser(String u, String e) { return db.createUser(u, e); }
    @Override protected void sendWelcome(String e, String u) { mail.send(e, "Welcome, " + u); }
    @Override protected void recordAudit(String entry) { audit.record(entry); }
}

// Test subclass — no infrastructure at all
class TestUserAccountManager extends UserAccountManager {
    public User existingUser = null;
    public boolean eligible = true;
    public String lastWelcomeTo;
    public String lastAudit;

    @Override protected User findUser(String u) { return existingUser; }
    @Override protected boolean hasEligibleRole(String u) { return eligible; }
    @Override protected User createUser(String u, String e) { return new User(u, e); }
    @Override protected void sendWelcome(String e, String u) { lastWelcomeTo = e; }
    @Override protected void recordAudit(String entry) { lastAudit = entry; }
}

@Test
public void rejectsProvisioningWhenUserAlreadyExists() {
    TestUserAccountManager mgr = new TestUserAccountManager();
    mgr.existingUser = new User("alice", "a@b.com");

    AccountResult r = mgr.provision("alice", "a@b.com");

    assertTrue(r.isExists());
    assertNull(mgr.lastWelcomeTo);
    assertNull(mgr.lastAudit);
}

The business logic of provision — uniqueness check, eligibility gate, sequence of side effects — is now fully testable with no infrastructure. The logic lives in the abstract base class; the glue lives in the production subclass.

Supporting and alternative techniques

Extract Interface (on each collaborator)

An alternative path: instead of pushing infrastructure down into a subclass, extract an interface from each infrastructure collaborator and inject all of them through the constructor. This produces a class with many constructor parameters but flat inheritance. Good when you want a future DI container to wire things up; bad when the parameter list grows to twelve. Push Down Dependency trades parameter count for inheritance depth.

Break Out Method Object

If part of the class is a giant method with its own entanglement problem, promote that method to its own class first. Sometimes a "large class" is really "one reasonable class plus one monster method" — splitting them reveals the real structure. See the pairing page for Monster-method dependency.

Pull Up Feature

The mirror operation: move a testable piece up into a new abstract parent class, leaving the untestable pieces in the now-subclass. Feathers describes it for situations where the pure-logic methods are a minority surrounded by infrastructure — you pull the minority up into a superclass whose tests can ignore the infrastructure subclass entirely.

Cautions and variations

Preserve the public interface

Callers of the original class shouldn't need to change. Keep the public methods on the abstract base class; keep their signatures identical. The subclass name is new, but the type callers depend on — through a base class reference or a factory — remains the one they knew.

Don't push down too eagerly

Not every field wants to move. Fields that are pure values (configuration flags, data structures, immutable lookup tables) belong in the base class. Only the problematic collaborators — the ones blocking tests — get pushed down.

Inheritance isn't free

You're adding a layer of inheritance that future developers have to understand. Document why: "ProductionUserAccountManager owns infrastructure wiring so that UserAccountManager can be unit-tested via TestUserAccountManager." A one-sentence comment at the top of the subclass saves future confusion.

Migrate toward composition eventually

Push Down Dependency is a legacy technique — it works on existing code without major restructuring. The cleaner end-state is usually composition: a UserAccountManager class that takes a UserRepository, EligibilityService, and Notifier as constructor parameters, each of which is a separately-designed interface. Once tests cover the logic, the refactor from inheritance to composition is safe and mechanical.

Related techniques not covered here. Parameterize Constructor is the right move when only one or two dependencies are problematic. Subclass and Override Method uses a similar inheritance trick for a much smaller scope — a single method, not whole categories of collaborators.
