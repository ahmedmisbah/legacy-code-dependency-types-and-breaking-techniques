Legacy Code: Java Dependency Types and Their Breaking Techniques

A pairing guide · Java dependency types · Feathers' dependency-breaking techniques

Michael Feathers' Working Effectively with Legacy Code catalogs twenty-four techniques for breaking dependencies so that legacy code can be brought under test. The techniques are organized as a reference alphabet, not as a flowchart — you're expected to recognize your situation and pick the right tool.

This site does the matching work for you. Each page pairs a Java dependency type (the shape of the problem you're facing in the code) with the Chapter 25 technique that Feathers recommends as the primary fix, plus the supporting techniques that handle adjacent cases. Every example is in Java, and every "Why this blocks tests" section is grounded in Feathers' sensing and separation framing from Chapter 3.

The final group, Beyond Chapter 25, covers Java dependency types the book doesn't name — time, randomness, filesystem, threading, and DI containers — because the relevant APIs and frameworks largely postdate the book's 2004 publication. The techniques there still apply Feathers' principles; they just use specific Java conventions that had to be invented later.

Fields and construction

Dependencies that live in the class itself — wired in when the object is created or accessed through its own fields.

  • Constructor Dependency → Parameterize Constructor
    The class creates its collaborators with new inside its constructor. The most common pattern and usually the easiest to fix.
  • Hidden Dependency → Extract and Override Factory Method
    The constructor makes decisions about which collaborator to build, not just a simple new. Move the logic into an overridable factory method.
  • Instance Variable Dependency → Extract and Override Getter
    The class holds a problematic collaborator as a field, sometimes lazy-initialized. Route every read through a getter a subclass can override.
  • Parameter Dependency → Extract Interface
    The method takes a concrete type that's hard to construct or fake. Lift the methods used into an interface; tests pass in a fake implementation.

Globals and static access

Dependencies that live outside the object graph — globals, singletons, static methods. No injection point at all, so the first job is creating one.

  • Global Reference Dependency → Encapsulate Global References
    Code reads System.getenv, static fields, or environment state directly. Wrap them in an object so the rest of the code stops noticing.
  • Singleton Dependency → Introduce Static Setter
    Code uses getInstance() to reach a shared service. Add a test-only static setter that lets tests substitute a fake.
  • Static Method Dependency → Introduce Instance Delegator
    Code calls Util.doSomething() with no seam. Create an instance method that delegates to the static; override it in a test subclass.

Call sites and external surface

Dependencies concentrated at specific lines of code or at the boundary with code you don't own.

  • Side-Effect Dependency → Extract and Override Call
    A method has one or two lines that do something tests can't tolerate (emails, writes, postings). Isolate each into a protected method a subclass can neutralize.
  • Library / Framework Dependency → Adapt Parameter
    The parameter's type is a framework class you can't modify (HttpServletRequest, ResultSet). Introduce your own interface and an adapter that wraps the framework type.

Scale problems

Dependencies that aren't one bad collaborator but an accumulation — too many to fix individually, or tangled up inside one giant unit.

  • Large-Class Dependency → Push Down Dependency
    A class has so many problematic collaborators that fixing them one at a time gets nowhere. Make the class abstract; push infrastructure into a production subclass; test via a test subclass.
  • Monster-Method Dependency → Break Out Method Object
    A method is so large that its locals are the dependencies — extract-method fails because every piece references every other piece. Promote the method to its own class where locals become fields.
  • Build-Time Dependency → Extract Interface
    The tests pass but nobody runs them because rebuilds take minutes. Pull a stable contract out of the concrete class so implementation changes stop forcing client recompilation.

Beyond Chapter 25

Java dependency types that Feathers' 2004 catalog doesn't name as techniques. In some cases (time, randomness) the relevant APIs hadn't been standardized yet. In others (DI containers, reactive streams) the frameworks that made these concerns common postdate the book. In all cases the principles remain Feathers' — every page here is an application of Parameterize Constructor, Encapsulate Global References, Extract Interface, Extract and Override Call, or Adapt Parameter — but the specific patterns are post-2004 Java conventions.

Non-deterministic primitives

Global access to a JDK primitive that returns a different answer every time — time and randomness being the canonical cases. The fix is Encapsulate Global References specialized to the primitive.

  • Time / Clock Dependency → Inject a Clock
    Code reaches for Instant.now() or System.currentTimeMillis(). Pass in a java.time.Clock; tests use Clock.fixed for frozen time or a mutable clock for simulated progression.
  • Randomness Dependency → Inject a Random Source
    Code calls Math.random(), ThreadLocalRandom, or UUID.randomUUID(). Inject a Random with a fixed seed and a Supplier<UUID>; tests become deterministic.

Concurrency

Code whose behavior depends on when work happens. Two distinct shapes: producing async work (where does it run?) and consuming async results (how do results come back?). Different seams, different fakes.

  • Threading / Concurrency Dependency → Inject an Executor
    Your code spawns threads or calls CompletableFuture.runAsync without an explicit executor. Inject an Executor; tests pass a synchronous one so async work becomes deterministic.
  • Async Result Dependency → Supply Pre-Completed Results
    Your code consumes CompletableFutures or callbacks from a collaborator. Extract an interface and fake it with CompletableFuture.completedFuture — no threading, no waiting, no flakiness.

External resources

I/O boundaries to things outside the JVM — disk, network, remote services. The fix is Adapt Parameter specialized to the specific boundary, combined with tooling the community has built for each one (Jimfs, WireMock, etc.).

  • Filesystem Dependency → Abstract the Filesystem
    Code uses Files.readAllBytes and new FileInputStream directly. Use Java NIO's FileSystem abstraction with Jimfs in tests, or a narrow interface you own.
  • Network / Protocol Dependency → Extract a Client Adapter
    Code calls a REST API, vendor SDK, or raw HTTP client directly. Pull the operations into an interface stated in your domain types; fakes for unit tests, WireMock for integration tests.

Framework and language constraints

Situations where Chapter 25 moves don't apply because the type system or framework forbids them — final classes that can't be subclassed, framework parents you can't modify, container-managed instantiation that tests can't reproduce, reflective calls that bypass normal type checking.

  • Inheritance Dependency → Compose Around the Inherited Type
    Your class is forced to extend a framework parent (HttpServlet, Spring controller, JPA entity base). Extract the business logic into a handler class you own; the framework class becomes a thin translator.
  • Final / Sealed Dependency → Wrap with a Hand-Written Adapter
    You depend on a final class or a class with final methods — Subclass and Override can't compile. Write a small interface and adapter you own, or reach for Mockito's mock-maker-inline.
  • DI Container Dependency → Bypass the Container
    A class uses field injection and container lifecycle hooks — tests have to boot Spring to do anything. Convert to constructor injection so tests can instantiate with new and skip the container entirely.
  • Reflection-Based Dependency → Wrap the Reflective Call
    Code uses Class.forName, Method.invoke, or dynamic proxies. Extract the reflective call into a protected method typed with your domain types; override it in a test subclass.
On the mapping. Feathers' book doesn't present techniques as strictly paired with dependency types — the Chapter 25 catalog is a prose reference rather than a lookup table. The pairings in the first four groups reflect one reasonable reading of which technique fits which problem first, with supporting techniques covering variations on each page. The fifth group, Beyond Chapter 25, covers Java dependency types that postdate the book; the fixes there apply Feathers' principles (most often Parameterize Constructor, Extract Interface, Adapt Parameter, Extract and Override Call, or Encapsulate Global References) to cases he couldn't have named. Many techniques apply across several dependency types — Extract Interface shows up twice in the first groups (parameter and build-time), underlies the network adapter and async-result pages, and appears as a supporting move on several others.
