The dependency

A parameter dependency appears when a method takes an argument whose type is difficult or impossible to instantiate in a test. The method's contract with its caller says "give me one of these" — but the caller, including your test, can't readily produce one. The painful types are usually concrete classes with heavy behavior (database clients, HTTP sessions, thread pools) or framework types whose construction requires a full runtime context.

Unlike a constructor dependency, a parameter dependency is visible at the call site. The type appears in the method signature, so anyone reading the code can see what's required. That makes it easier to reason about than hidden dependencies — but it doesn't make it easier to test, because you still have to supply the real thing (or find another way) every time you want to exercise the method.

Why this blocks tests

Parameter dependencies produce a specific flavor of the sensing/separation problem: the method itself is accessible (you can call it from a test), but what you have to pass in isn't.

The parameter may be impossible to construct

Types like HttpServletRequest, ResultSet, or an internal framework request wrapper are not instantiable in isolation. They assume a servlet container, a JDBC driver, or a live framework runtime. Your test can't just call new on them.

The parameter's real behavior drags in real infrastructure

Even when the parameter can be constructed, using a real one often means real I/O. Passing a real PaymentGateway means real charges; passing a real Database means real queries. The test inherits every problem of the real collaborator.

You can't observe what the method did to the parameter

If the method mutates the parameter or calls methods on it, the test wants to see that. With a concrete type and no handle on its internal state, the only way to check is through the parameter's own observable interface — which, for framework types, is usually backed by the same infrastructure you were trying to avoid.

Type coupling propagates to every caller

The concrete parameter type doesn't just affect this method. Everywhere this method is called, the caller has to produce that concrete type. The testing problem multiplies as it spreads through the callers.

Sensing vs. separation here. Extract Interface gives you a test-controlled implementation you can pass in (separation) and inspect afterwards (sensing). One technique, both problems solved.

The technique: Extract Interface

Extract Interface pulls the methods the caller actually invokes on the parameter into a new interface. The method's signature changes to accept the interface rather than the concrete class. The original concrete class is declared to implement the interface, so production code keeps working unchanged. In tests, you supply a hand-written fake that implements the same interface.

Feathers calls it one of the safest techniques in the catalog. The concrete class keeps all its code; the interface is a pure declaration of methods the class already has. Mistakes tend to be caught by the compiler.

When to use it

  • The parameter's type is a class you control (you can add implements to it).
  • The method under test calls only a handful of the parameter's methods — you want a narrow interface reflecting actual use, not an exhaustive mirror.
  • You want a technique that's safe to apply without tests already in place.

When not to use it:

  • The parameter is a framework or third-party type you can't modify — use Adapt Parameter instead.
  • The parameter's class is final and you can't unseal it — again, Adapt Parameter or a hand-written wrapper.

Example

Before — ReportGenerator.generate takes a concrete DataSource that opens real database connections:

public class DataSource {
    public DataSource(String jdbcUrl, Credentials creds) {
        // opens a real connection pool
    }

    public ResultSet query(String sql) { /* live query */ }
    public void close() { /* ... */ }
    public ConnectionStats stats() { /* ... */ }
}

public class ReportGenerator {
    public Report generate(DataSource dataSource, DateRange range) {
        ResultSet rs = dataSource.query("SELECT ... WHERE date BETWEEN ...");
        return buildReport(rs);
    }
}

Any test of generate has to supply a DataSource, which means a real connection pool.

Steps

  1. List the methods that ReportGenerator.generate actually calls on the DataSource parameter. In this case, just query.
  2. Create an interface declaring those methods, using a name focused on the role (QueryRunner) rather than the class (DataSource).
  3. Declare the original concrete class to implement the interface. No method changes are required — the class already has the methods.
  4. Change the parameter type in generate from DataSource to the new interface.
  5. In tests, create a fake that implements the interface and returns canned data.

Example (after)

public interface QueryRunner {
    ResultSet query(String sql);
}

public class DataSource implements QueryRunner {
    // unchanged — the class already had a query(String) method
}

public class ReportGenerator {
    public Report generate(QueryRunner runner, DateRange range) {
        ResultSet rs = runner.query("SELECT ... WHERE date BETWEEN ...");
        return buildReport(rs);
    }
}

// In tests
public class FakeQueryRunner implements QueryRunner {
    public String lastSql;

    @Override
    public ResultSet query(String sql) {
        lastSql = sql;
        return FakeResultSet.withRows(sampleData());
    }
}

@Test
public void generatesReportFromQueryResults() {
    FakeQueryRunner fake = new FakeQueryRunner();
    Report report = new ReportGenerator().generate(fake, DateRange.lastMonth());

    assertNotNull(report);
    assertTrue(fake.lastSql.contains("BETWEEN"));
}

Supporting and alternative techniques

Adapt Parameter

When the parameter's class is a framework or third-party type you can't modify, you can't declare implements on it. Adapt Parameter is the workaround: define your own interface, write a small adapter that wraps the framework object and delegates to it, and change the method signature to take your interface instead of the framework type.

Before — populate takes a Servlet API type:

public void populate(HttpServletRequest request) {
    String[] values = request.getParameterValues("pageState");
    // ...
}

After — a small interface you control, an adapter for production, a fake for tests:

public interface ParameterSource {
    String[] getValues(String name);
}

public class HttpRequestAdapter implements ParameterSource {
    private final HttpServletRequest request;
    public HttpRequestAdapter(HttpServletRequest r) { this.request = r; }
    @Override
    public String[] getValues(String name) { return request.getParameterValues(name); }
}

public void populate(ParameterSource source) {
    String[] values = source.getValues("pageState");
    // ...
}

Subclass and Override Method

If the parameter's class is yours but you'd rather not introduce a new interface (perhaps because only this one test site needs to vary its behavior), you can subclass the parameter's class and override the specific methods the code under test calls. Pass an instance of the subclass in the test. This keeps the production signature unchanged, but it only works when the class isn't final and the methods aren't final.

Primitivize Parameter

Occasionally the parameter's class is so hard to fake that a cleaner path is to write a helper method working on primitives or simple value types, call it from the original method, and test the helper directly. This leaves the original method with the awkward parameter untested, but covers its core logic. Feathers presents it as a fallback when interface extraction isn't viable.

Cautions and variations

Keep the interface lean

The temptation is to mirror every public method of the class onto the interface. Resist it. Put only the methods that this particular caller actually invokes. A narrow interface communicates intent ("this method needs something that can run queries") and supports the Interface Segregation Principle.

Name after the role, not the class

Don't call the interface IDataSource or DataSourceInterface. Call it what the parameter does in this context — QueryRunner, PriceLookup, MessageSink. Good names signal role, not implementation.

Signature preservation

When copying methods into the interface, copy them verbatim — same parameter names, same throws clauses, same return types. Retyping invites subtle drift that the compiler can't always catch.

Related techniques not covered here. Extract Implementer is the C++ variant of Extract Interface (renames the concrete class instead of adding an interface on top) — rarely needed in Java, where tool support for Extract Interface is excellent. Parameterize Method is a sibling for cases where you want to pass something different into a method without introducing a new type at all.
