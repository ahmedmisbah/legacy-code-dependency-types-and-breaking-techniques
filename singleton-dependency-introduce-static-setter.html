The dependency

A singleton dependency shows up wherever code reaches out to a class's getInstance() method (or equivalent static accessor) to obtain a shared object. The singleton owns its own construction, enforces uniqueness through a private constructor, and hands the same instance to everyone who asks. In tests, you inherit whatever the singleton is — there's no parameter, no field, no constructor argument to redirect.

Singletons combine two testability obstacles at once: they're globals (always the same instance) and they're typically heavyweight services (database connections, HTTP clients, configuration loaders). Every test that touches a class using the singleton indirectly drags the singleton along for the ride.

Why this blocks tests

Always the same instance

The point of a singleton is that getInstance() always returns the same object. In tests, that's exactly what you don't want — you want different test cases to see different behavior, and you want parallel test runs not to interfere with each other.

State leaks across tests

Singletons often hold state (caches, counters, connection pools). One test pollutes the singleton; the next test inherits the pollution. Test order becomes load-bearing. Developers learn to distrust the suite.

Eager initialization runs real work at class-load time

Many singletons instantiate themselves in a static initializer or on first access. If that instantiation talks to a database or reads a file, merely loading the class in a test triggers real I/O — before your test has even started.

The calling code has no injection point

Unlike a parameter or a field, a getInstance() call has nowhere for a caller to intervene. The class under test reaches out to the singleton directly, skipping every mechanism you'd normally use to substitute it.

The technique: Introduce Static Setter

Introduce Static Setter opens a controlled back door: add a static method that lets tests replace the singleton instance with a fake. The setter is deliberately scoped (package-private or protected) so production code can't accidentally use it. Before each test, the setter installs a fake; after the test, the suite restores the real instance or resets the singleton.

The technique doesn't solve the underlying design problem — you still have a singleton. What it does is create a seam where none existed, so the class that uses the singleton can at least be tested. Feathers presents it as a stepping-stone: get tests in place, then refactor toward proper dependency injection once the tests protect you.

When to use it

  • You have a singleton that many classes touch via getInstance().
  • You own the singleton class (you can add a static setter to it).
  • You need tests in place now and can't afford to eliminate the singleton first.

When not to use it:

  • The singleton comes from a third-party library and you can't modify it — consider wrapping it with an adapter instead.
  • Only one class uses the singleton — Extract Interface on the singleton plus field injection is cleaner.

Example

Before — CheckoutController reaches into PaymentProcessor.getInstance() every time it runs:

public class PaymentProcessor {
    private static final PaymentProcessor INSTANCE = new PaymentProcessor();

    private PaymentProcessor() {
        // opens a real HTTPS connection to the payment gateway
    }

    public static PaymentProcessor getInstance() { return INSTANCE; }

    public ChargeResult charge(Customer c, Money amount) { /* live call */ }
}

public class CheckoutController {
    public Receipt checkout(Order order) {
        ChargeResult r = PaymentProcessor.getInstance()
            .charge(order.getCustomer(), order.getTotal());
        if (!r.ok()) throw new PaymentFailedException();
        return new Receipt(order, r.getTxId());
    }
}

Merely loading PaymentProcessor opens the HTTPS connection. There is nowhere for a test to stop this.

Steps

  1. Make the singleton's instance field non-final so it can be reassigned.
  2. Relax the constructor's visibility enough that a test subclass can call it (or expose a test-only constructor).
  3. Add a package-private or protected static setter — typically named setTestingInstance or similar — that assigns a new instance to the field.
  4. Add a reset method that restores the original instance (often just by constructing a fresh one or by caching the original reference).
  5. In tests, create a subclass of the singleton with overridden methods, call the setter in @Before, and call the reset in @After.

Example (after)

public class PaymentProcessor {
    private static PaymentProcessor instance = new PaymentProcessor();

    protected PaymentProcessor() { // now subclass-able from tests }

    public static PaymentProcessor getInstance() { return instance; }

    // Package-private: only tests in the same package can use it
    static void setTestingInstance(PaymentProcessor testInstance) {
        instance = testInstance;
    }

    static void resetInstance() {
        instance = new PaymentProcessor();
    }

    public ChargeResult charge(Customer c, Money amount) { /* live call */ }
}

// Test subclass overrides the behavior we don't want
class FakePaymentProcessor extends PaymentProcessor {
    public Money lastAmount;
    public boolean succeed = true;

    @Override
    public ChargeResult charge(Customer c, Money amount) {
        lastAmount = amount;
        return succeed ? ChargeResult.ok("test-1") : ChargeResult.fail();
    }
}

@Test
public void checkoutChargesCustomerTotal() {
    FakePaymentProcessor fake = new FakePaymentProcessor();
    PaymentProcessor.setTestingInstance(fake);
    try {
        new CheckoutController().checkout(Order.of(Money.usd(49.99)));
        assertEquals(Money.usd(49.99), fake.lastAmount);
    } finally {
        PaymentProcessor.resetInstance();
    }
}

Nothing has changed for production callers — they still call getInstance() and receive the real processor. The test has a seam it didn't have before.

Supporting and alternative techniques

Subclass and Override Method (on the singleton)

When you want to keep things self-contained in a single test and don't want to touch static state, you can sometimes bypass the singleton altogether: subclass the singleton, override the method you care about, and arrange for the code under test to use your subclass via another seam. This only works when the code under test uses the singleton through a reference you can inject — which, for classic Java singletons, is exactly the thing that's missing. When it applies, though, it avoids the global-state juggling that Introduce Static Setter requires.

Extract Interface on the singleton

A stepping-stone toward eliminating the singleton entirely. Extract an interface from the singleton's class, have clients accept the interface through their constructors (via Parameterize Constructor), and pass the singleton in at the composition root. The singleton is still there, but nobody except the composition root reaches for getInstance() anymore. Tests inject a fake implementation of the interface.

Cautions and variations

Teardown is mandatory

A test that calls setTestingInstance and doesn't reset leaves the fake in place for every subsequent test in the JVM. Put the reset in an @After method, a try/finally, or a test-framework fixture — not in the test body alone, where an assertion failure would skip it.

Parallel tests are unsafe

The setter writes shared global state. Two tests running simultaneously will clobber each other's fakes. Mark any class using this technique as serial, or migrate to constructor injection before enabling parallel test execution.

Static setters invite misuse

Even with package-private visibility, a static setter signals "mutable global" to anyone browsing the code. Some future developer will use it from production code to paper over a bug. Counter-measures: name the setter unmistakably (setForTestingOnly), put a Javadoc comment explaining its purpose, consider guarding it with a debug-only flag.

It doesn't fix the design

The singleton is still a singleton. The test seam is a patch, not a solution. Once tests cover the code, migrate toward proper injection: have clients accept the singleton's type as a constructor argument, and have a single top-level wiring point pass in the real instance.

Related techniques not covered here. Encapsulate Global References targets raw globals (static fields, environment variables) — apply it when the global isn't a proper singleton but just a shared mutable value. Introduce Instance Delegator is the right fix when the problem is a static method rather than a singleton instance.
