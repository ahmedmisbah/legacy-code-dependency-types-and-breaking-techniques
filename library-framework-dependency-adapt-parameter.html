Library / Framework Dependency

Java dependency type · Chapter 25 fix: Adapt Parameter

The dependency
Library / Framework Dependency
The technique
Adapt Parameter

The dependency

A library or framework dependency arises when your code is coupled to a type you don't own and can't modify: HttpServletRequest, ResultSet, a vendor's SDKClient, or a type declared final or sealed in someone else's JAR. You can't add implements to it. You can't subclass it. You may not even be able to construct it without a full framework runtime (servlet container, JDBC driver, cloud SDK).

This is the dependency type Feathers' Extract Interface technique doesn't solve directly — Extract Interface requires that you can declare the existing class as implementing a new interface, which is precisely what you can't do here. Adapt Parameter is the workaround.

Why this blocks tests

You can't modify the class

The class's source isn't yours to change. You can't add an interface, you can't add methods, you can't relax final. The standard dependency-breaking techniques that rely on touching the class's source don't apply.

You often can't construct it

Framework types typically assume they're being created by the framework itself. HttpServletRequest is produced by the servlet container; a ResultSet comes from a live JDBC Statement. Even if you could instantiate one, the constructor may require infrastructure your tests don't have.

It's often final or sealed

Many library types are deliberately locked down. Subclassing to override a method (the standard fallback) doesn't compile. Feathers calls this the restricted override dilemma: design constraints meant to protect consumers from misuse also prevent testing.

Mocking frameworks help but have limits

Tools like Mockito can produce instances of framework types (via bytecode generation), which lets you stub methods. That's convenient, but it ties every test to the mocking framework, makes failures harder to diagnose, and doesn't work at all for truly final classes without special configuration. A hand-written adapter is often more durable.

The technique: Adapt Parameter

Adapt Parameter introduces a new interface that you own, declaring the methods your code actually needs from the library type. The method under test takes this interface instead of the library type. In production, an adapter class wraps the real library object and delegates calls to it. In tests, you implement the interface directly with a fake.

The key insight is that your code usually needs only a tiny slice of the library type's surface. HttpServletRequest has dozens of methods; your method may call two. The interface captures just those two, your adapter forwards just those two, and the test implements just those two.

When to use it

  • A method takes (or uses) a framework / library type you can't modify.
  • Your method uses a small, well-defined subset of the type's methods.
  • You want tests that don't require the framework runtime.

When not to use it:

  • You own the library type — Extract Interface is simpler (no adapter needed).
  • Your code uses the framework type extensively across many methods — a focused adapter per use-site makes more sense than one giant one.

Example

Before — FormProcessor.populate takes a raw HttpServletRequest:

public class FormProcessor {
    public void populate(HttpServletRequest request) {
        String[] values = request.getParameterValues("pageState");
        if (values != null && values.length > 0) {
            applyState(values[0]);
        }

        String referrer = request.getHeader("Referer");
        if (referrer != null) {
            trackReferrer(referrer);
        }
    }
}

Testing populate means constructing or mocking an HttpServletRequest — a sprawling interface with dozens of methods and complicated implementations.

Steps

  1. List the methods your code actually calls on the library type. Here: getParameterValues, getHeader.
  2. Define a new interface with just those methods, named for the role the parameter plays (not for the library). FormRequest, say.
  3. Write an adapter class that implements the interface and delegates to the library type.
  4. Change the method signature to accept the interface instead of the library type.
  5. At production call sites, wrap the library object in the adapter: populate(new ServletFormRequest(httpRequest)).
  6. In tests, implement the interface with a fake — often a simple inner class or lambda.

Example (after)

// The interface — only the methods FormProcessor actually needs
public interface FormRequest {
    String[] parameter(String name);
    String header(String name);
}

// Adapter for production — delegates to the real framework type
public class ServletFormRequest implements FormRequest {
    private final HttpServletRequest req;
    public ServletFormRequest(HttpServletRequest req) { this.req = req; }

    @Override
    public String[] parameter(String name) { return req.getParameterValues(name); }

    @Override
    public String header(String name) { return req.getHeader(name); }
}

// The class under test now takes the interface
public class FormProcessor {
    public void populate(FormRequest request) {
        String[] values = request.parameter("pageState");
        if (values != null && values.length > 0) applyState(values[0]);

        String referrer = request.header("Referer");
        if (referrer != null) trackReferrer(referrer);
    }
}

// Production call site
processor.populate(new ServletFormRequest(httpServletRequest));

// Test — no servlet container, no mocking framework needed
@Test
public void populateAppliesPageStateParameter() {
    FormRequest fake = new FormRequest() {
        @Override
        public String[] parameter(String name) {
            return name.equals("pageState") ? new String[] { "active" } : null;
        }
        @Override
        public String header(String name) { return null; }
    };

    new FormProcessor().populate(fake);

    assertEquals("active", currentPageState());
}

Supporting and alternative techniques

Extract Interface (via wrapper)

A close cousin of Adapt Parameter that applies when the library type's entire role in your system can be captured in one interface, not just the slice used at one call site. The difference is organizational: Adapt Parameter typically creates a narrow per-use-site interface; Extract Interface via wrapper creates one broader interface that multiple methods in your codebase depend on. Both techniques rely on the same fundamental trick — an adapter class you own bridges the library type to an interface you own.

Hand-written fakes over mocking frameworks

Not a Chapter 25 technique, but worth noting alongside Adapt Parameter: once the adapter is in place, you could use Mockito to mock the interface. Hand-written fakes are often clearer, don't require framework setup, compile-time-check themselves, and remain readable years later. For any fake you use across many tests, invest in a named class rather than a lambda or a mock.

Cautions and variations

Name the interface after your role, not the library

The library type might be HttpServletRequest, but your interface should be FormRequest, IncomingMessage, or whatever describes the role in your system. Naming by role keeps the interface stable across library versions and makes the code read better at the point of use.

The adapter should be dumb

Every method on the adapter should be a single-line delegation. No caching, no logging, no error translation. Put any smartness in a higher layer. A fat adapter develops its own testing problems.

Keep the interface minimal

Expand the interface only when a new method genuinely needs the library's capability. Resist the reflex to expose "all the useful methods" — each additional method is one more thing every fake has to implement.

Library upgrades become safer

A secondary benefit worth calling out: when the library changes (HttpServletRequest gains new methods, or the vendor renames something), only the adapter has to track those changes. Your core logic and every test continue to compile unchanged. This is one of the few dependency-breaking techniques that materially improves production code beyond testability.

Related techniques not covered here. When the library type is one you do own and can modify, Extract Interface is simpler and doesn't require an adapter. When the library problem is actually a method (a static call) rather than a parameter, use Introduce Instance Delegator.
