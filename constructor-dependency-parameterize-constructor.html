Constructor Dependency

Java dependency type · Chapter 25 fix: Parameterize Constructor

Constructor Dependency
The technique
Parameterize Constructor

The dependency

A constructor dependency appears when a class instantiates its own collaborators directly inside its constructor using new. The collaborator is sealed in at construction time — no outside caller can choose a different one, and no test can substitute a fake. If the collaborator talks to a real database, spawns a thread pool, opens a socket, or reads from the filesystem, the class it belongs to inherits all of those behaviors whether you want them in a test or not.

In Java this pattern is so common it's almost invisible. A field declared and initialized at the declaration site (private final Logger log = LoggerFactory.getLogger(...)) is a constructor dependency. A new call in the constructor body is a constructor dependency. A static factory call like DbConnection.get() inside the constructor is a constructor dependency. The class owns its collaborators, which sounds tidy until you try to write a test.

Why it's worth naming. Constructor dependencies are Feathers' hidden dependency case at its most literal: the wiring is buried inside construction logic, invisible to anyone reading the class's public API. You can't see what the class depends on without opening its source and reading the constructor body.

Why this blocks tests

Constructor dependencies are especially hostile to testing because they defeat both halves of Feathers' sensing and separation problem at the same time. You can't run the class without also running its collaborators, and you can't observe what the class did to them. Every specific pain below is a consequence of one or the other.

You can't substitute (the separation failure)

The new call inside the constructor isn't a choice — it's a fact. Every time a test writes new OrderService(), a real SmtpEmailSender and a real InventoryClient spring into existence along with it. There is no place to intervene. A test that was supposed to verify a small piece of ordering logic ends up exercising the mail server and the database, whether the test author wanted that or not.

You can't observe (the sensing failure)

Even if the real collaborators happen to work in the test environment, the test has no handle on them. It can't ask the email sender "were you called, and with what arguments?" because that object is sealed inside the class. The only signal you can check is downstream side effects — a real inbox, a real row in the database — which requires the real infrastructure and brings back every problem from the first point.

The constructor might refuse to run at all

If the environment isn't right — SMTP host unreachable, database credentials missing, configuration file absent — the constructor throws before the test can do anything useful. A class that can't be instantiated can't be tested. This is how legacy codebases end up with no unit tests at all: the entry-point classes require half of production to spin up, so nobody even tries.

Determinism and speed collapse together

Calls like Clock.systemUTC() or UUID.randomUUID() embedded in the constructor make every test run slightly different. A test that asserts on a timestamp can never be stable. And because each test drags real I/O-backed collaborators into existence, microsecond-scale unit tests become second-scale integration tests — which discourages running them often, which defeats the point of having tests in the first place.

Error paths become nearly untestable

Testing "what happens when the payment processor declines?" means causing a real decline against a real gateway, which means test cards, sandbox accounts, and flaky networks. Testing "what happens when the database is down?" means somehow bringing the database down during a test run. With a real collaborator welded in place, every failure mode of every collaborator is out of reach — which means the most important paths in the code, the ones that handle things going wrong, are the least tested.

The dependency is invisible at the API

A reader looking at OrderService's public surface sees a class with a no-argument constructor and naturally concludes it's self-contained. The fact that it needs a working SMTP server, a reachable database, and a system clock surfaces only at runtime — often in production, as a stack trace from a deployment that forgot to set an environment variable. Constructor dependencies don't just block tests; they hide the shape of the system from everyone who reads the code.

Connecting back. Every technique in the rest of this page attacks one or both halves of the sensing/separation problem. Parameterize Constructor gives the test a way to substitute the collaborator (separation) and a reference to hold on to afterwards (sensing). That's why it's the default fix for this dependency type — one move solves both problems.

The technique: Parameterize Constructor

Parameterize Constructor lifts the new call out of the constructor and turns it into a parameter. The class no longer decides which collaborator it uses — the caller does. In production, the caller passes in the real implementation. In a test, the caller passes in a fake. The class itself doesn't know or care which is which.

This is the simplest and most widely applicable technique in Feathers' catalog for Java code. It's also the technique that modern Java conventions (constructor injection, Spring, Guice, Dagger) have quietly institutionalised — applying it by hand is exactly what a DI container does automatically.

When to use it

  • The constructor contains one or more new SomeThing() calls where SomeThing is painful or impossible to use in a test.
  • You own the source of the class and can change its constructor.
  • The set of callers is either small, or you're willing to keep a convenience constructor for ones you can't update.
  • You want injection without pulling in a full DI framework just to break this one dependency.

When not to use it:

  • When the dependency is so entangled with other constructor logic that cleanly extracting it is risky — consider Extract and Override Factory Method instead, which leaves construction alone and intercepts creation through a protected method.
  • When changing the constructor signature would break a large number of callers you don't control — keep the old constructor as a convenience overload that delegates to the new one.

Example

Before — OrderService hard-codes its collaborators in the constructor. Nothing outside the class can redirect them:

public class OrderService {
    private final EmailSender emailSender;
    private final InventoryClient inventory;
    private final Clock clock;

    public OrderService() {
        this.emailSender = new SmtpEmailSender(System.getenv("SMTP_HOST"));
        this.inventory = new InventoryClient(DbConnection.get());
        this.clock = Clock.systemUTC();
    }

    public Receipt placeOrder(Order order) {
        inventory.reserve(order.getItems());
        emailSender.sendConfirmation(order.getCustomer(), order);
        return new Receipt(order, clock.instant());
    }
}

Any test of placeOrder is actually a test of SMTP configuration, database connectivity, and the wall clock. The class appears to take no dependencies — its no-argument constructor is a polite lie.

Steps

Feathers' sequence is designed to preserve existing behavior while opening the door to injection. Work one collaborator at a time:

  1. Identify the collaborator you want to pull out — one new call in the constructor.
  2. Add a parameter of the collaborator's type to the constructor, matching the field's declared type. Preserve all other parameters and their order exactly (Feathers' Preserve Signatures rule).
  3. In the constructor body, replace the new call with a simple assignment from the new parameter.
  4. Update callers to pass in the real implementation. If you can't update every caller, keep a no-arg convenience constructor that delegates to the new one using this(...).
  5. Repeat for each remaining collaborator until the constructor does nothing but assign incoming parameters to fields.
  6. In tests, instantiate the class with fake implementations.

Example (after)

After — collaborators are injected, and a convenience constructor preserves the old signature for legacy callers:

public class OrderService {
    private final EmailSender emailSender;
    private final InventoryClient inventory;
    private final Clock clock;

    // Parameterized constructor — this is the one tests and new callers use
    public OrderService(EmailSender emailSender,
                        InventoryClient inventory,
                        Clock clock) {
        this.emailSender = emailSender;
        this.inventory = inventory;
        this.clock = clock;
    }

    // Convenience constructor — preserves the old no-arg signature
    // so callers that haven't been updated still work.
    public OrderService() {
        this(new SmtpEmailSender(System.getenv("SMTP_HOST")),
             new InventoryClient(DbConnection.get()),
             Clock.systemUTC());
    }

    public Receipt placeOrder(Order order) {
        inventory.reserve(order.getItems());
        emailSender.sendConfirmation(order.getCustomer(), order);
        return new Receipt(order, clock.instant());
    }
}

Now the test has somewhere to plug in:

@Test
public void placeOrderReservesInventoryAndEmailsConfirmation() {
    FakeEmailSender email = new FakeEmailSender();
    FakeInventory inv = new FakeInventory();
    Clock fixed = Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), ZoneOffset.UTC);

    OrderService service = new OrderService(email, inv, fixed);
    Receipt receipt = service.placeOrder(Order.sample());

    assertTrue(inv.reserveWasCalled);
    assertEquals("jane@example.com", email.lastRecipient);
    assertEquals(Instant.parse("2026-01-01T00:00:00Z"), receipt.getTimestamp());
}

Notice that the clock dependency — one of the gaps we identified earlier in Feathers' catalog — falls out for free. Parameterize Constructor plus a Clock interface is exactly the recipe the time dependency row of the gap table points to.

Supporting and alternative techniques

Parameterize Constructor is the first thing to try, but two situations make it awkward: a constructor that does genuinely complex creation logic (conditional branches, configuration-driven wiring, lazy setup), and a constructor you aren't allowed to change at all. Feathers gives each situation its own technique.

Extract and Override Factory Method

Use this when the constructor doesn't just call new — it makes decisions about what to create. Parameterising such a constructor forces every caller to reproduce those decisions, which is the opposite of what you want. The fix: leave the decision logic where it is, but move it into a protected method. Production behaviour is unchanged, and a test subclass can override the method to return a fake.

Steps:

  1. Identify the creation expression inside the constructor.
  2. Extract it into a protected method with a name that describes what's being created (e.g., createInventoryClient).
  3. Call the new method from the constructor.
  4. In tests, subclass the class and override the factory method to return a fake.

Before — the constructor decides which variant of InventoryClient to wire up:

public class OrderService {
    private final InventoryClient inventory;

    public OrderService(Config config) {
        this.inventory = config.isProduction()
            ? new InventoryClient(config.dbUrl(), config.getRetries())
            : new InventoryClient("memory://local", 0);
    }
}

After — the decision logic moves into a protected factory method:

public class OrderService {
    private final InventoryClient inventory;

    public OrderService(Config config) {
        this.inventory = createInventoryClient(config);
    }

    protected InventoryClient createInventoryClient(Config config) {
        return config.isProduction()
            ? new InventoryClient(config.dbUrl(), config.getRetries())
            : new InventoryClient("memory://local", 0);
    }
}

// Test subclass — overrides creation without touching the constructor
public class TestableOrderService extends OrderService {
    public TestableOrderService(Config config) {
        super(config);
    }

    @Override
    protected InventoryClient createInventoryClient(Config config) {
        return new FakeInventoryClient();
    }
}
Initialization-order gotcha. Because the factory method is called from within the superclass constructor, it runs before any fields declared in the test subclass are initialised. That's why the override above returns a new FakeInventoryClient() inline rather than a field that the subclass tried to set first. If you need the fake to be configurable from the test, capture it in a static holder or use an overload that accepts a pre-built fake through super(...).

Supersede Instance Variable

Use this when you truly cannot change the constructor — typically because it's inherited, overridden by reflection-based frameworks, or called from code you can't touch. The idea is to let the constructor run normally, then overwrite one of its fields from the outside afterwards. Feathers treats this as a last resort. It breaks encapsulation, leaves the real object's construction side effects in place, and invites misuse; but sometimes it's the only technique available.

Steps:

  1. Add a public method that assigns a new value to the instance variable.
  2. Give it an unmistakably test-only name (Feathers' convention: supersedeX where X is the field name).
  3. In tests, construct the object normally, then call the superseder to replace the real collaborator with a fake.

Before — a constructor you can't modify (perhaps because it's part of a framework-invoked lifecycle or a legacy entry point used by dozens of call sites):

public class LegacyOrderService {
    private Clock clock;
    // ... many other fields, wired up by 200 lines of construction logic

    public LegacyOrderService(ComplicatedConfig cfg) {
        // long, untouchable initialization
        this.clock = Clock.systemUTC();
        // ... 200 more lines
    }

    public Receipt placeOrder(Order order) {
        return new Receipt(order, clock.instant());
    }
}

After — a deliberately-named setter replaces the field after construction:

public class LegacyOrderService {
    private Clock clock;
    // ... many other fields, unchanged

    public LegacyOrderService(ComplicatedConfig cfg) {
        // original construction logic untouched
        this.clock = Clock.systemUTC();
        // ...
    }

    // Deliberately ugly name — signals test-only intent
    public void supersedeClock(Clock newClock) {
        this.clock = newClock;
    }
}

@Test
public void receiptUsesInjectedClock() {
    LegacyOrderService service = new LegacyOrderService(ComplicatedConfig.defaults());
    service.supersedeClock(Clock.fixed(Instant.EPOCH, ZoneOffset.UTC));

    Receipt r = service.placeOrder(Order.sample());

    assertEquals(Instant.EPOCH, r.getTimestamp());
}

The real Clock.systemUTC() still runs during construction (and any side effects with it), but by the time the test exercises placeOrder, the field points at the fake. Feathers considers Supersede Instance Variable acceptable only when nothing cleaner is available; once the codebase tolerates changes, migrate to Parameterize Constructor and delete the superseder.

Cautions and variations

Parameter list growth

Each dependency you extract adds a parameter. A class with six collaborators ends up with a six-argument constructor, which is ugly and pushes toward the Long Parameter List smell. That's the honest trade-off Feathers acknowledges: testability now, cosmetic cleanup later. If the list grows genuinely unmanageable, it's a signal that the class itself is doing too much — split it, don't cover the problem with a builder.

Convenience constructor vs. no default

The convenience no-arg constructor is useful when callers can't all be updated at once, but it has a cost: it hides the dependencies from the type system again and can quietly keep the bad pattern alive for years. Once the caller list is manageable, delete the convenience constructor and force every caller to declare what it's wiring in.

Pair with Extract Interface

Parameterize Constructor alone isn't enough if the collaborator's type is a concrete class that's still painful to construct. Combine it with Extract Interface: extract an interface from the collaborator, parameterize the constructor with the interface type, and pass a fake that implements the interface in tests. This pair of techniques covers the majority of real Java dependency-breaking work.

Related techniques not covered here. Parameterize Method is a narrower sibling — when the dependency is only used by one method, pass it as a method argument instead of a constructor argument. Extract Interface is the almost-always companion: extract an interface from the collaborator's type, then parameterize the constructor with the interface rather than a concrete class. Extract and Override Factory Method and Supersede Instance Variable are covered in full above.
