Time / Clock Dependency

Java dependency type · Modern Java technique: Inject a Clock

The dependency
Time / Clock Dependency
The technique
Inject a Clock
Not in Chapter 25. Feathers' catalog doesn't name a technique for time. The closest principle is Encapsulate Global References, and the closest shape of fix is Parameterize Constructor with the wrapped global. What's new here is that modern Java provides a standard type — java.time.Clock (added in Java 8, 2014) — so the encapsulation has a canonical name, API, and test helpers. The book, published in 2004, pre-dates all of it.

The dependency

A time / clock dependency appears wherever code reaches for the system clock: System.currentTimeMillis(), Instant.now(), LocalDateTime.now(), new Date(), Calendar.getInstance(). Each call consults the OS, returns whatever it reports, and moves on. The class using these calls is bound to the wall clock.

Anything time-dependent inherits the problem: session expirations, business-hours checks, retry backoffs, cache TTLs, daily batch cutoffs, log timestamps, audit trails, discount windows. All of them read now implicitly, and every test of them is at the mercy of when it happens to run.

Why this blocks tests

Every test run produces a different timeline

A test that checks "an order 25 hours old should be expired" gets a different absolute timestamp each run. The relative assertion might hold, but any log, audit entry, or returned object containing Instant.now() is different every time — so assertions on those fields either approximate (which hides bugs) or capture the current time and pretend that was the expected value (which is circular).

Boundary cases require waiting or fakery

Testing "what happens at midnight UTC?" or "what happens when daylight saving time ends?" requires either waiting for the real time to get there, running the test at the right moment, or setting the system clock — all bad options. Most teams give up and leave these paths untested, which is where bugs live.

Past and future dates are unreachable

You can't easily test a class that behaves differently in 2099 without falsifying the system clock. The same applies to "what did this system do last year" kinds of backfill logic. Real time only flows forward at one speed.

Flaky tests erode trust

Tests that pass most of the time because of a near-boundary condition (a sleep, a timing assumption) train the team to ignore failures. The suite becomes folklore rather than a truth source. Deterministic time removes this class of flakiness entirely.

The technique: Inject a Clock

Inject a Clock replaces direct calls to time primitives with calls on an injected java.time.Clock instance. The class's constructor takes a Clock; production wiring passes Clock.systemDefaultZone() or Clock.systemUTC(); tests pass Clock.fixed(instant, zone) for a frozen clock or a custom mutable clock for simulated time progression.

The clock becomes the single point where the class asks what time is it?. Every time-dependent API in java.time accepts a Clock as an overload: Instant.now(clock), LocalDateTime.now(clock), ZonedDateTime.now(clock). There is no escape hatch from the injected clock unless the code explicitly avoids it.

When to use it

  • Any class whose behavior depends on the current time.
  • Tests need to verify time-dependent logic deterministically.
  • You can change the class's constructor (or use an existing DI mechanism).
  • The codebase is on Java 8 or later.

When not to use it:

  • The codebase is pre-Java-8 and can't upgrade — roll your own TimeSource wrapper with the same shape.
  • Time is used only in one method for logging a timestamp that no test will ever assert on — injection is overkill for passive uses.

Example

Before — OrderService reads the wall clock directly:

public class OrderService {
    private static final Duration EXPIRY = Duration.ofHours(24);

    public boolean isExpired(Order order) {
        return Duration.between(order.getCreatedAt(), Instant.now())
            .compareTo(EXPIRY) >= 0;
    }

    public Order submit(Cart cart) {
        return new Order(cart, Instant.now());
    }
}

Testing isExpired at exactly the 24-hour boundary requires carefully constructing an order whose createdAt is 24 hours before now, which means either capturing Instant.now() in the test (making the test a circular self-check), or sleeping, or doing arithmetic the test itself depends on.

Steps

  1. List every call to a time primitive in the class: Instant.now(), LocalDateTime.now(), System.currentTimeMillis(), new Date(), and so on.
  2. Add a Clock clock field and a constructor parameter for it.
  3. Add a convenience no-arg constructor that defaults to Clock.systemUTC() (or systemDefaultZone()) so existing callers don't break.
  4. Replace each time-primitive call with the clock-aware variant: Instant.now(clock), LocalDateTime.now(clock), clock.millis(), Date.from(clock.instant()).
  5. In tests, pass Clock.fixed(Instant.parse("..."), ZoneOffset.UTC) for frozen time, or a custom mutable clock for tests that need to advance time within a single test.

Example (after)

public class OrderService {
    private static final Duration EXPIRY = Duration.ofHours(24);
    private final Clock clock;

    public OrderService(Clock clock) { this.clock = clock; }
    public OrderService() { this(Clock.systemUTC()); }

    public boolean isExpired(Order order) {
        return Duration.between(order.getCreatedAt(), Instant.now(clock))
            .compareTo(EXPIRY) >= 0;
    }

    public Order submit(Cart cart) {
        return new Order(cart, Instant.now(clock));
    }
}

@Test
public void orderExpiresExactlyAt24Hours() {
    Instant createdAt = Instant.parse("2026-04-20T10:00:00Z");
    Clock at24Hours = Clock.fixed(createdAt.plus(Duration.ofHours(24)), ZoneOffset.UTC);

    OrderService svc = new OrderService(at24Hours);
    assertTrue(svc.isExpired(Order.createdAt(createdAt)));
}

@Test
public void orderNotYetExpiredAt23Hours59Minutes() {
    Instant createdAt = Instant.parse("2026-04-20T10:00:00Z");
    Instant almost24h = createdAt.plus(Duration.ofHours(23).plusMinutes(59));
    Clock clock = Clock.fixed(almost24h, ZoneOffset.UTC);

    OrderService svc = new OrderService(clock);
    assertFalse(svc.isExpired(Order.createdAt(createdAt)));
}

Both boundary cases are now deterministic and require no sleeping, no real-time math, no system clock manipulation.

Supporting and alternative techniques

A mutable clock for progression tests

When the test needs time to advance within a single run — a session timing out mid-test, a cache TTL expiring — Clock.fixed isn't enough. A small mutable clock makes this easy:

public class MutableClock extends Clock {
    private Instant now;
    private final ZoneId zone;

    public MutableClock(Instant start) { this(start, ZoneOffset.UTC); }
    public MutableClock(Instant start, ZoneId zone) {
        this.now = start; this.zone = zone;
    }

    @Override public Instant instant() { return now; }
    @Override public ZoneId getZone() { return zone; }
    @Override public Clock withZone(ZoneId z) { return new MutableClock(now, z); }

    public void advance(Duration d) { now = now.plus(d); }
}

The test manually advances the clock where real code would have waited.

Extract and Override Getter (pre-Java-8 fallback)

If you can't take the constructor-injection route — pre-Java-8 codebase, or a class that genuinely can't have its constructor changed — fall back to Feathers' Extract and Override Getter: wrap time access in a protected method (protected Instant now() { return Instant.now(); }) and override it in a test subclass. Less clean than Clock injection but works anywhere.

Cautions and variations

Don't mix clock-aware and clock-free calls

Once a class has a Clock, every time reference should go through it. One stray Instant.now() defeats the whole exercise and produces tests that fail mysteriously under load. Static analysis rules (or a git grep) help enforce discipline.

Be consistent about zones

UTC is safest for tests. Production may use systemDefaultZone(), but if your domain logic cares about local time (billing cycles, delivery windows), make the zone an explicit concern — never rely on the JVM's default zone silently affecting behavior.

Spring and other DI containers make this trivial

Declaring a @Bean Clock clock() { return Clock.systemUTC(); } in a Spring configuration class lets every @Autowired constructor receive the clock automatically. Tests override the bean with @TestConfiguration providing a fixed or mutable clock.

Logging timestamps are usually fine to leave alone

The clock-injection discipline applies to business logic that depends on time. Log frameworks have their own timestamping that isn't part of the class's behavior and doesn't need the same treatment. Keep the scope clear.
