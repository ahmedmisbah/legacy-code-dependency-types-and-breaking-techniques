Side-Effect Dependency

Java dependency type · Chapter 25 fix: Extract and Override Call

The dependency
Side-Effect Dependency
The technique
Extract and Override Call

The dependency

A side-effect dependency exists inside a method: one or more specific lines do something you can't tolerate during a test — post to a remote service, write a file, send an email, touch a message queue, emit a metric to a monitoring system. The rest of the method is perfectly testable in principle; the problem is these individual call sites.

This differs from a constructor or field dependency in that the offending behavior is narrowly localised. You don't need to inject a whole collaborator to fix it — you just need a seam around one call. That's exactly what Extract and Override Call provides.

Why this blocks tests

Running the method performs real side effects

A test that calls logOrder(order) expecting to verify the formatting logic will also, as a side effect, post a real audit entry to the live audit service. Even if the test doesn't assert on the posted entry, the entry still happens.

Side effects pollute shared environments

Writes to shared queues, files, or databases accumulate across test runs. Tests that ran in the past leave traces that affect tests running now. CI environments drift from developer machines because side effects have accumulated differently.

You can't verify the side effect without specialised infrastructure

To check whether a side effect occurred, you'd need to intercept it outside the process — run a real audit service in the test, read a real file back, consume from a real queue. Each of these is an entire integration-testing stack to cover a single line of code.

Error paths are untestable

The offending call may throw, retry, or block. Without a seam, you can't simulate "the audit service is down" or "the file write fails". The error handling around the call is effectively uncovered.

The technique: Extract and Override Call

Extract and Override Call isolates a problem call into its own method, then overrides that method in a test subclass. The offending line moves from the middle of a larger method into a one-line protected method whose only job is to make that call. A test subclass overrides the method to do nothing, record what was asked, or throw a simulated error.

Feathers treats it as a precise, surgical technique: it neutralizes exactly one call site without reorganizing anything around it. The method under test remains otherwise unchanged. Only the targeted line is replaceable.

When to use it

  • A method contains one or two specific calls whose side effects you can't run in tests.
  • The rest of the method is testable — the side-effect call is the sole obstacle.
  • The class isn't final and the method you want to override isn't static or final.

When not to use it:

  • Many side-effecting calls are scattered through the method — the whole method probably wants a different treatment (Break Out Method Object or splitting responsibilities).
  • The call is to a static method — use Introduce Instance Delegator, which is the static-specific variant of the same idea.

Example

Before — AuditLogger.logOrder formats and validates an entry, then posts it externally:

public class AuditLogger {
    public void logOrder(Order order) {
        String entry = formatEntry(order);
        validateEntry(entry);
        ExternalAuditService.post(entry);  // live HTTP POST to an audit server
    }

    private String formatEntry(Order o) { /* real formatting logic */ }
    private void validateEntry(String e) { /* real validation */ }
}

The formatting and validation are exactly what you'd want to test. The HTTP POST is exactly what you'd want to stop from happening.

Steps

  1. Identify the single call in the method that has the problematic side effect.
  2. Extract it into a protected instance method whose body is just that call. Use Preserve Signatures — copy the argument list and return type verbatim.
  3. Replace the original call with a call to the new method.
  4. In tests, subclass the class and override the extracted method with a no-op, a recorder, or a fake that throws to simulate failure.

Example (after)

public class AuditLogger {
    public void logOrder(Order order) {
        String entry = formatEntry(order);
        validateEntry(entry);
        postToAuditService(entry);
    }

    protected void postToAuditService(String entry) {
        ExternalAuditService.post(entry);
    }

    private String formatEntry(Order o) { /* unchanged */ }
    private void validateEntry(String e) { /* unchanged */ }
}

// Test subclass that records instead of posting
class RecordingAuditLogger extends AuditLogger {
    public String lastPosted;

    @Override
    protected void postToAuditService(String entry) {
        lastPosted = entry;
    }
}

@Test
public void logOrderFormatsAndValidatesBeforePosting() {
    RecordingAuditLogger logger = new RecordingAuditLogger();
    logger.logOrder(Order.of(Money.usd(49.99), "cust-123"));

    assertNotNull(logger.lastPosted);
    assertTrue(logger.lastPosted.contains("cust-123"));
    assertTrue(logger.lastPosted.startsWith("ORDER:"));
}

@Test
public void logOrderPropagatesPostFailures() {
    AuditLogger logger = new AuditLogger() {
        @Override
        protected void postToAuditService(String entry) {
            throw new AuditDownException();
        }
    };
    assertThrows(AuditDownException.class, () -> logger.logOrder(Order.sample()));
}

Supporting and alternative techniques

Subclass and Override Method

If the offending call is the bulk of the method — most of the logic is the side effect — extracting it into its own method produces a one-liner next to a method with nothing interesting in it. In that case, override the whole method in the test subclass instead. Extract and Override Call is for the case where the method has meaningful logic around the side effect; Subclass and Override Method is for the case where the side effect is the method.

Before — method that does little but the side effect:

public void notify(User user, Event event) {
    EmailService.send(user.getEmail(), event.asMessage());
}

After — override the whole method:

public void notify(User user, Event event) {
    EmailService.send(user.getEmail(), event.asMessage());
}
// no extraction needed — the method itself is the seam

class TestNotifier extends Notifier {
    public User lastNotified;
    @Override
    public void notify(User user, Event event) { lastNotified = user; }
}

Break Out Method Object

When the method in question is so large and tangled that extracting just one call isn't safe — or when many side-effecting calls are woven through the method — the heavier technique is to promote the entire method into its own class. Locals become fields; each side-effecting call becomes a protected method on the new class, each of which can be overridden independently. See the pairing page for Monster-method dependency for the full treatment.

Cautions and variations

Don't move any logic into the extracted method

The discipline is strict: the extracted method contains only the problem call. Any pre-processing of arguments, any post-processing of return values, stays in the original method. If you move logic into the extracted method, you lose test coverage of that logic in the subclass.

Watch for multiple side effects in one line

A call like ExternalAuditService.post(entry).onFailure(retry) does two things that want to be substitutable separately. Either split the call first, or extract the entire expression and override as a unit (losing some granularity).

Anonymous subclasses are fine for one-off tests

If you only need the override for one test, an anonymous subclass at the test site is perfectly readable and avoids creating a separate named class for every variation. For reused test doubles, a named subclass is clearer.

Related techniques not covered here. Introduce Instance Delegator is the variant used when the side-effecting call is a static method (like ExternalAuditService.post in the example above). The two techniques are close cousins; the choice depends on whether the target of the call is an instance or a class.
