Filesystem Dependency

Java dependency type · Modern Java technique: Abstract the Filesystem

The dependency
Filesystem Dependency
The technique
Abstract the Filesystem
Not in Chapter 25. Feathers' catalog doesn't name a technique specifically for filesystem access. The closest matches are Extract Interface or Adapt Parameter — wrap I/O operations in a narrow interface you own. What's new is that modern Java offers two canonical tools: the java.nio.file.FileSystem abstraction (Java 7, 2011) and Jimfs, Google's in-memory FileSystem implementation designed specifically for tests.

The dependency

A filesystem dependency appears wherever code reads or writes files directly: Files.readAllBytes(path), new FileInputStream(file), Files.write(path, bytes), File.createTempFile(...), Files.walk(...). Each of these touches the real filesystem — opens real file handles, consumes real disk I/O, may be subject to real permissions, real disk-full conditions, real filesystem case-sensitivity rules.

Common places this bites: configuration loading at startup, certificate and key file access, report output, batch file processing, log file rotation, resource extraction from archives, cache files, anywhere code does import/export. The testing problem is the same in every case — real I/O leaks into the test, and tests need real files arranged in real directories before they can run.

Why this blocks tests

Real I/O is slow and flaky

A unit test that reads a 1 KB config file still pays a syscall, a disk seek (on spinning media), filesystem cache warm-up, and operating-system overhead. Multiply across hundreds of tests and the suite goes from seconds to minutes. Under load — on a shared CI runner — timings get noisy and previously-green tests go yellow.

Tests pollute each other

If two tests write to /tmp/out.csv, ordering starts mattering. If one test forgets to clean up, the next inherits its files. Parallel test execution is unsafe by default — you have to manually partition directories or serialize the suite.

Setup becomes a chore

Every test of a file-reading class needs a real file to exist at a specific path with specific content. That means either checking test fixtures into version control (which accumulate forever) or constructing the file in the test's @Before (which is noisy). Both make tests harder to read and maintain.

Error paths are effectively unreachable

To test "what happens when the disk is full", you'd need to actually fill the disk. "What happens on a permission error", "what if the file is locked by another process", "what if the path is longer than the filesystem allows" — all similarly impractical with a real filesystem. An abstracted filesystem can be programmed to throw at will.

Platform differences surface in production

Real filesystems vary: Windows uses case-insensitive paths and different separators; macOS may normalize Unicode filenames; some networked filesystems have timing quirks. Tests that pass on one platform fail subtly on another. An in-memory filesystem gives predictable semantics regardless of host OS.

The technique: Abstract the Filesystem

Abstract the Filesystem has two common shapes. The first — the narrow approach — introduces a small interface (FileStore, ConfigReader, ReportWriter) capturing just the I/O operations the class actually uses. Production implements the interface by delegating to java.nio.file; tests implement it with an in-memory map.

The second — the broad approach — uses Java NIO's built-in java.nio.file.FileSystem abstraction. Your code receives a FileSystem instance (or accepts Path values from one) and uses it for everything. In production, pass FileSystems.getDefault(). In tests, pass a Jimfs-backed filesystem: Jimfs.newFileSystem(Configuration.unix()) gives you a complete in-memory POSIX-like filesystem with no test-visible differences from the real thing.

The narrow approach adds less machinery and is right for code that does a few specific things with files. The broad approach is right for code that does substantial filesystem work (walks trees, manages temp directories, deals with multiple paths) where you want the full API surface available to tests.

When to use it

  • A class does file I/O that tests need to cover deterministically.
  • Tests would otherwise require fixture files, temp-dir management, or platform-specific setup.
  • You want to cover error paths (disk full, permission denied, missing file) that real filesystems resist producing.

When not to use it:

  • The class's purpose is real filesystem behavior — a disk-backup tool, for instance. Tests should exercise the real filesystem (carefully scoped to temp dirs).
  • File I/O is already behind a well-tested library call that has its own test seam — don't double-wrap.

Example

Before — ConfigLoader reads directly via java.nio.file:

public class ConfigLoader {
    public Config load(String configDir) throws IOException {
        Path main = Paths.get(configDir, "app.yaml");
        Path overrides = Paths.get(configDir, "overrides.yaml");

        String mainYaml = Files.readString(main);
        Config config = Config.parse(mainYaml);

        if (Files.exists(overrides)) {
            String ovYaml = Files.readString(overrides);
            config = config.mergeWith(Config.parse(ovYaml));
        }
        return config;
    }
}

Testing this means creating real files in a real directory. Testing the error case (main file missing, overrides file malformed) means arranging those conditions on disk. Parallel tests must not share the config dir.

Steps (broad approach — Jimfs)

  1. Identify the methods and classes that currently call Paths.get or the static Files methods.
  2. Accept a FileSystem (or Path values derived from one) as a constructor parameter. Default to FileSystems.getDefault() for callers who don't care.
  3. Replace Paths.get(...) with fileSystem.getPath(...).
  4. Keep using Files.readString, Files.exists, etc. — they work against any FileSystem as long as the Path values come from that FileSystem.
  5. In tests, construct a Jimfs filesystem, populate it with the files the test needs, and pass it to the class under test.

Example (after)

public class ConfigLoader {
    private final FileSystem fs;

    public ConfigLoader(FileSystem fs) { this.fs = fs; }
    public ConfigLoader() { this(FileSystems.getDefault()); }

    public Config load(String configDir) throws IOException {
        Path main = fs.getPath(configDir, "app.yaml");
        Path overrides = fs.getPath(configDir, "overrides.yaml");

        String mainYaml = Files.readString(main);
        Config config = Config.parse(mainYaml);

        if (Files.exists(overrides)) {
            config = config.mergeWith(Config.parse(Files.readString(overrides)));
        }
        return config;
    }
}

// Test — entirely in memory, no real disk, runs in milliseconds
@Test
public void loadAppliesOverridesWhenPresent() throws IOException {
    FileSystem fs = Jimfs.newFileSystem(Configuration.unix());
    Path dir = fs.getPath("/conf");
    Files.createDirectory(dir);
    Files.writeString(dir.resolve("app.yaml"), "port: 80");
    Files.writeString(dir.resolve("overrides.yaml"), "port: 8080");

    Config cfg = new ConfigLoader(fs).load("/conf");

    assertEquals(8080, cfg.getPort());
}

@Test
public void loadThrowsWhenMainConfigMissing() throws IOException {
    FileSystem fs = Jimfs.newFileSystem(Configuration.unix());
    Files.createDirectory(fs.getPath("/conf"));

    assertThrows(NoSuchFileException.class,
        () -> new ConfigLoader(fs).load("/conf"));
}

Supporting and alternative techniques

Extract Interface (narrow approach)

When the class uses a small, well-defined slice of filesystem operations, skip the full FileSystem abstraction and define your own interface:

public interface FileStore {
    String read(String path) throws IOException;
    boolean exists(String path);
}

public class NioFileStore implements FileStore {
    @Override
    public String read(String path) throws IOException {
        return Files.readString(Paths.get(path));
    }
    @Override
    public boolean exists(String path) { return Files.exists(Paths.get(path)); }
}

// Test fake — backed by a plain Map
public class InMemoryFileStore implements FileStore {
    private final Map<String, String> files = new HashMap<>();
    public void put(String path, String content) { files.put(path, content); }
    @Override
    public String read(String path) throws IOException {
        String c = files.get(path);
        if (c == null) throw new NoSuchFileException(path);
        return c;
    }
    @Override
    public boolean exists(String path) { return files.containsKey(path); }
}

Less infrastructure, less dependency (no Jimfs), less API surface to learn. Preferred when the class genuinely only does a few things with files.

JUnit 5 @TempDir

Not an abstraction at all, but a pragmatic middle ground: JUnit 5's @TempDir annotation gives each test a fresh temporary directory, automatically cleaned up afterward. It doesn't remove the real-I/O cost, but it eliminates the cross-test-pollution problem and is standard JUnit with no extra dependencies. Use it when the class under test really needs real filesystem behavior, but not when pure logic would benefit from Jimfs.

Extract and Override Call

For a single problematic file operation in an otherwise testable method, Feathers' Extract and Override Call is a lighter touch than the full abstraction: wrap the one call in a protected method, override in a test subclass.

Cautions and variations

Jimfs is an additional dependency

Jimfs is a Google-maintained library, not part of the JDK. Teams that minimize dependencies may prefer the narrow interface approach. For teams that already depend on Guava ecosystem libraries, Jimfs is essentially free.

Mind the filesystem semantics you're emulating

Jimfs ships with Configuration.unix(), Configuration.windows(), and Configuration.osX(). Pick the one that matches production, or your tests may pass on the test's filesystem but fail on production's. If production runs on Linux, use Configuration.unix().

Watch for Path-to-String conversions

A Path from a Jimfs filesystem is not interchangeable with a Path from FileSystems.getDefault(). If your class stringifies a Path and later reconstructs it via Paths.get, the reconstructed path points at the real filesystem, not the test one. Keep Path values flowing through the injected FileSystem rather than round-tripping them through strings.

Real-I/O integration tests still have their place

Unit tests with an in-memory filesystem are fast and deterministic; they don't replace integration tests that verify actual I/O behavior. Keep a small set of tests that use the real filesystem to catch platform-specific issues that in-memory abstractions don't reproduce (file locking semantics, networked filesystems, permission edge cases).
