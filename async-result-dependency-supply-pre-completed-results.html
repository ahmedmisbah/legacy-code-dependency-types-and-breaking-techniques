Async Result Dependency

Java dependency type · Modern Java technique: Supply Pre-Completed Results

The dependency
Async Result Dependency
The technique
Supply Pre-Completed Results
Not in Chapter 25, and distinct from threading. The Threading / Async Dependency → Inject an Executor pairing covers "my code produces async work" — you inject an executor and use a synchronous one in tests. This pairing covers the other async shape: "my code consumes async results from a collaborator that returns CompletableFutures or calls me back". The fix is Extract Interface on the collaborator plus a fake that returns already-completed futures (or invokes callbacks synchronously). Both patterns appear in the same codebase, but they're different seams in different directions.

The dependency

An async result dependency exists when your class collaborates with something that delivers results asynchronously — a repository that returns CompletableFuture<User>, an SDK client that takes a callback, a reactive stream source, a message bus that invokes a listener. The async is part of the collaborator's contract; it's not something your class chose to introduce. Your class has to compose with the future chain or register a callback, and the result arrives (or fails) at some later time.

Common shapes: Spring WebFlux controllers returning Mono; AWS SDK v2 async clients that hand back CompletableFuture; gRPC stubs with callback-based APIs; reactive database drivers (R2DBC) that emit rows through Publisher; Kafka consumers with onRecord callbacks. Testing code that uses any of these is not about "when does my work run?" — it's about "how do I hand my code a fake async result that the test can fully control?"

Why this blocks tests

Real futures complete on background threads

A real CompletableFuture returned by a real collaborator is likely to complete on an I/O thread, a gRPC worker, or a reactor scheduler. Tests that call into your code and then check state immediately see the state before the async completion. Classic race: the test finishes before the collaborator delivers.

You can't join your way out of every problem

Adding .get() on the future blocks the test thread until completion. Sometimes this works. Often it creates new problems: deadlocks when the collaborator dispatches back onto the test thread, timeout flakiness when the collaborator is slow, or silent failure when the collaborator never completes. Blocking is a workaround, not a fix.

Callback APIs have no return value to wait on

A collaborator whose interface is void fetch(String id, Callback callback) doesn't give you a handle to await. Your test either sleeps, uses a CountDownLatch (which every test has to remember to count down correctly), or instruments the callback directly — none of which tests the code that's actually interesting.

Error paths fire at surprising times

A real failed future may propagate its exception through handle, exceptionally, whenComplete, or catch blocks down the chain. Reproducing this in a test with a real collaborator means making the collaborator fail in exactly the right way — which typically means controlling something outside the test's reach (a network, a downstream service).

The technique: Supply Pre-Completed Results

Supply Pre-Completed Results extracts an interface for the async collaborator (often it's already defined by the library) and implements it in tests with fakes that return results already resolved. For CompletableFuture-returning methods, the fake returns CompletableFuture.completedFuture(value) (or CompletableFuture.failedFuture(exception)). For callback-based APIs, the fake invokes the callback synchronously before returning. For reactive streams, the fake emits onto a synchronous scheduler.

When the collaborator's async is short-circuited to "already done", the code under test proceeds as if there were no async at all. The chain of .thenApply and .thenCompose still runs — it just runs synchronously because each stage's prerequisite is immediately available. Assertions after the call see the final state without any waiting or blocking.

When to use it

  • Your class depends on a collaborator with an async-shaped contract (future-returning, callback-based, or reactive).
  • You're testing your class's logic, not the collaborator's timing behavior.
  • The collaborator is (or can be made) behind an interface you control at the test boundary.

When not to use it:

  • The thing you want to test is the timing behavior — e.g., "if the future takes longer than 2 seconds, we should time out". Use a controlled scheduler instead.
  • The code under test composes futures from many collaborators and you want to verify specific interleavings — integration tests with real schedulers are more appropriate.

Example

Before — OrderFulfiller uses an async payment gateway that returns CompletableFuture:

public interface AsyncPaymentGateway {
    CompletableFuture<ChargeResult> charge(Money amount, String customerId);
}

public class OrderFulfiller {
    private final AsyncPaymentGateway gateway;
    private final OrderRepository orders;

    public OrderFulfiller(AsyncPaymentGateway g, OrderRepository o) {
        this.gateway = g;
        this.orders = o;
    }

    public CompletableFuture<Receipt> fulfill(Order order) {
        return gateway.charge(order.getTotal(), order.getCustomerId())
            .thenApply(result -> {
                if (!result.ok()) throw new PaymentFailedException(result.reason());
                order.markPaid(result.transactionId());
                orders.save(order);
                return new Receipt(order, result.transactionId());
            });
    }
}

The interface already exists (AsyncPaymentGateway). The problem isn't extracting it; it's controlling what its charge method returns in tests — and specifically, doing so without async machinery that makes the test await something.

Steps

  1. Confirm the collaborator has an interface (extract one if not — Extract Interface from Ch 25 applies).
  2. In tests, implement the interface with a fake. For future-returning methods, return CompletableFuture.completedFuture(value) or CompletableFuture.failedFuture(ex). For callback-based methods, invoke the callback synchronously before returning.
  3. Drive the code under test. Because every stage's prerequisite is already resolved, each .thenApply runs immediately on the calling thread.
  4. Assert on the returned future's state: isDone(), join() (safe — won't block), or isCompletedExceptionally().

Example (after)

// Fake — returns results instantly, no thread switch
public class FakePaymentGateway implements AsyncPaymentGateway {
    public Money lastAmount;
    public String lastCustomer;
    private ChargeResult next = ChargeResult.ok("txn-1");
    private RuntimeException nextError;

    public void willReturn(ChargeResult r) { this.next = r; this.nextError = null; }
    public void willFailWith(RuntimeException e) { this.nextError = e; }

    @Override
    public CompletableFuture<ChargeResult> charge(Money amount, String customerId) {
        this.lastAmount = amount;
        this.lastCustomer = customerId;
        if (nextError != null) return CompletableFuture.failedFuture(nextError);
        return CompletableFuture.completedFuture(next);
    }
}

@Test
public void fulfillMarksOrderPaidAndSaves() {
    FakePaymentGateway gw = new FakePaymentGateway();
    gw.willReturn(ChargeResult.ok("txn-abc"));
    InMemoryOrderRepository repo = new InMemoryOrderRepository();

    OrderFulfiller f = new OrderFulfiller(gw, repo);
    Order order = Order.of("cust-1", Money.usd(99.99));

    Receipt receipt = f.fulfill(order).join(); // safe — future is already done

    assertEquals("txn-abc", receipt.getTransactionId());
    assertTrue(order.isPaid());
    assertSame(order, repo.findById(order.getId()));
    assertEquals(Money.usd(99.99), gw.lastAmount);
}

@Test
public void fulfillPropagatesPaymentGatewayFailures() {
    FakePaymentGateway gw = new FakePaymentGateway();
    gw.willFailWith(new GatewayTimeoutException("upstream timed out"));

    OrderFulfiller f = new OrderFulfiller(gw, new InMemoryOrderRepository());
    CompletableFuture<Receipt> future = f.fulfill(Order.of("cust-1", Money.usd(1)));

    assertTrue(future.isCompletedExceptionally());
    CompletionException ex = assertThrows(CompletionException.class, future::join);
    assertInstanceOf(GatewayTimeoutException.class, ex.getCause());
}

@Test
public void fulfillRejectsPaymentDeclines() {
    FakePaymentGateway gw = new FakePaymentGateway();
    gw.willReturn(ChargeResult.declined("insufficient funds"));

    OrderFulfiller f = new OrderFulfiller(gw, new InMemoryOrderRepository());
    CompletableFuture<Receipt> future = f.fulfill(Order.of("cust-1", Money.usd(1)));

    assertTrue(future.isCompletedExceptionally());
}

No thread switches, no waiting, no sleeps. The future chain runs to completion on the calling thread because every stage's prerequisite is already there. .join() is safe to call — it confirms completion but doesn't block.

Supporting and alternative techniques

Synchronous callbacks

For callback-based APIs, the fake invokes the callback inline before returning:

public interface AsyncUserService {
    void fetch(String id, Consumer<User> onSuccess, Consumer<Throwable> onError);
}

public class FakeAsyncUserService implements AsyncUserService {
    private User nextUser;
    public void willReturn(User u) { this.nextUser = u; }

    @Override
    public void fetch(String id, Consumer<User> onSuccess, Consumer<Throwable> onError) {
        if (nextUser != null) onSuccess.accept(nextUser);
        else onError.accept(new NotFoundException(id));
    }
}

The callback runs on the test thread, before fetch returns. Code under test sees the result immediately.

Reactor Test (StepVerifier) for Project Reactor

Projects using Reactor (Mono, Flux) have a standard test utility: StepVerifier in the reactor-test library. It drives the stream synchronously and makes assertions about emissions and timing. The underlying principle is the same — supply a source that's pre-resolved to the test's liking — but the tooling is specific to Reactor.

Extract Interface (Ch 25)

If the async collaborator doesn't already have an interface, use Feathers' Extract Interface first. Once the interface exists, pre-completion becomes the fake's business rather than the collaborator's.

A controlled scheduler for time-sensitive tests

When the test wants to verify behavior at specific async timings (timeouts, retries with backoff), pre-completed results don't help. Use a controllable scheduler — Guava's DeterministicScheduler, Reactor's VirtualTimeScheduler, or a hand-rolled time-stepping executor — and inject it alongside the clock.

Cautions and variations

Beware thread-confinement assumptions

Real code under test may assume that certain stages run on non-caller threads (UI frameworks especially). A pre-completed future causes those stages to run on the test thread, which may surface thread-confinement bugs. That's usually a good thing — the bugs are real and were invisible in production. Occasionally it's a bad thing — the test now fails for reasons unrelated to the behavior it's trying to verify. When this happens, the code's thread-confinement assumption needs to be made explicit, typically by dispatching back onto a known executor.

Don't mock CompletableFuture itself

Mocking CompletableFuture produces confusion — the class has dozens of methods that interact in subtle ways. Mock the collaborator that returns the future, and let the fake return real CompletableFuture instances (pre-completed). Real futures compose correctly with your .thenApply chain; mocked ones don't.

Delayed completion is sometimes intentional

If you need to test "my code should still hold the lock while waiting for the future to complete", pre-completion defeats the test — the wait becomes instant. Use new CompletableFuture<>() (a future deliberately left incomplete) and complete it at the moment the test wants:

CompletableFuture<ChargeResult> deferred = new CompletableFuture<>();
gateway.onCharge(() -> deferred);

// ... test setup, verify lock is held ...
deferred.complete(ChargeResult.ok("txn-1"));
// ... verify state after completion ...

Don't test the library's async

Your tests should verify your code's behavior given various async outcomes. They shouldn't verify that CompletableFuture correctly propagates exceptions (it does), or that Reactor's operators respect backpressure (they do). Those are the library's tests to pass, not yours.
