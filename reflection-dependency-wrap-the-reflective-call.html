Not in Chapter 25. Feathers' catalog treats reflection by implication: the static calls (Class.forName, Method.invoke, Proxy.newProxyInstance) are a flavor of global reference, and the fix — Extract and Override Call — applies. What isn't in the book is specific guidance for reflective code, which has its own peculiarities: class-loading side effects, checked exceptions that ripple through signatures, results typed as Object, and dynamic proxy creation at runtime. Treat this pairing as Feathers' technique applied deliberately to reflection's particular shape.

The dependency

A reflection-based dependency exists when code uses Java's reflection API to inspect or invoke types at runtime — typically Class.forName(name), class.getMethod(...).invoke(...), Constructor.newInstance(...), Proxy.newProxyInstance(...), annotation-processor APIs, or service-loader-style dynamic discovery. The reflective call is a global (it reaches into the classloader's world to find a type by name) and a side-effect (class loading runs static initializers), rolled into one.

Common shapes: plugin systems that load user classes by name; serialization libraries that construct DTOs from JSON via reflection; framework bootstrap code that scans the classpath for annotated types; migration tools that fall back to reflective field access when getters don't exist. Any of these makes the containing class depend not on a compile-time type but on the runtime classloader state — which tests have very little control over.

Why this blocks tests

The classloader is a global

Class.forName("com.example.Plugin") looks up the class in a classloader that's shared across the whole JVM (or at least the whole test run). If the class doesn't exist in the classpath, the call fails. If it exists but its static initializer has side effects, those side effects happen during the test. Neither is controllable from within a single test without classloader surgery.

Reflective invocations have surprising error paths

Method.invoke wraps any exception thrown by the target in InvocationTargetException. Constructor.newInstance adds InstantiationException and IllegalAccessException. Test assertions about "what exception was thrown" have to navigate the wrapping, and unwrapping requires understanding of how reflection exposes failures. Accidental assertions on the wrong exception type pass tests that miss real bugs.

Results are typed Object

Reflective invocation returns Object. The surrounding code casts. Tests that try to stub reflection must return plausibly-typed values, or the cast blows up. A mock that returns null (default for unstubbed methods) often gets through the reflection layer and fails later at a cast, far from the test's actual intent.

Proxy-based code is especially opaque

Code that uses Proxy.newProxyInstance to create runtime implementations of interfaces (JDK dynamic proxies, bytecode libraries like Byte Buddy) produces classes that don't exist in your source tree. Tests can observe their behavior but can't step through them in a debugger without understanding the proxy's internal dispatching.

The technique: Wrap the Reflective Call

Wrap the Reflective Call is Extract and Override Call from Feathers' Ch 25, applied deliberately to reflection's specific shape. The reflective call — ideally just one line — moves into its own protected method whose signature uses concrete types (the kind of object the caller wants, not Object). The method body performs the reflection and casts on the way out. Test subclasses override the method to return a canned instance, bypassing reflection entirely.

The wrapping buys two things at once: it gives the test a seam, and it concentrates the reflection's type erasure into one well-documented place. The rest of the class can work with typed values, unaware that reflection is happening behind the scenes.

When to use it

  • Code uses reflection to load, construct, or invoke types identified by name or by annotation.
  • Tests need to verify behavior without depending on specific classes existing on the classpath.
  • The class isn't final and a test subclass is feasible.

When not to use it:

  • The reflection is the class's purpose — a plugin loader, an annotation processor — in which case testing means loading real test fixtures via the same mechanism. Small targeted fixtures, not mocking, is the right tool.
  • The reflection is used only to work around an access modifier (calling a private method from outside its class). Fix the access modifier; don't wrap the reflection.

Example

Before — PluginLauncher loads and instantiates plugins by class name:

public class PluginLauncher {
    public PluginResult launch(String pluginClass, PluginConfig config) {
        try {
            Class<?> cls = Class.forName(pluginClass);
            Plugin plugin = (Plugin) cls.getDeclaredConstructor().newInstance();
            plugin.configure(config);
            return plugin.run();
        } catch (ReflectiveOperationException e) {
            throw new PluginStartupFailed(pluginClass, e);
        }
    }
}

Testing launch's happy path requires a real plugin class on the classpath. Testing error paths requires arranging specific failure modes (non-existent class, class with a private constructor, class that throws from its constructor) — each of which means writing a dedicated fixture class. The test surface is wide and the test classes are numerous.

Steps

  1. Identify the reflective call. Here it's the whole Class.forName → newInstance sequence, which together produce a Plugin.
  2. Extract it into a protected method with a signature typed to the caller's needs: protected Plugin loadPlugin(String className).
  3. The method body keeps the reflection; the caller's code above it sees only typed values.
  4. Translate checked reflection exceptions into a domain exception inside the method — callers shouldn't see ReflectiveOperationException.
  5. In tests, subclass and override loadPlugin to return a pre-constructed fake plugin instance.

Example (after)

public class PluginLauncher {
    public PluginResult launch(String pluginClass, PluginConfig config) {
        Plugin plugin = loadPlugin(pluginClass);
        plugin.configure(config);
        return plugin.run();
    }

    protected Plugin loadPlugin(String className) {
        try {
            Class<?> cls = Class.forName(className);
            return (Plugin) cls.getDeclaredConstructor().newInstance();
        } catch (ReflectiveOperationException e) {
            throw new PluginStartupFailed(className, e);
        }
    }
}

// Test subclass — overrides the reflection seam with a fake plugin
class TestPluginLauncher extends PluginLauncher {
    public String lastLoadedName;
    private Plugin nextPlugin;
    private PluginStartupFailed nextError;

    public void willReturn(Plugin p) { this.nextPlugin = p; this.nextError = null; }
    public void willFailWith(PluginStartupFailed e) { this.nextError = e; }

    @Override
    protected Plugin loadPlugin(String className) {
        this.lastLoadedName = className;
        if (nextError != null) throw nextError;
        return nextPlugin;
    }
}

// Minimal fake plugin for tests
class FakePlugin implements Plugin {
    public PluginConfig configured;
    private PluginResult result = PluginResult.ok();
    public void willReturn(PluginResult r) { this.result = r; }

    @Override public void configure(PluginConfig c) { this.configured = c; }
    @Override public PluginResult run() { return result; }
}

@Test
public void launchConfiguresPluginBeforeRunning() {
    FakePlugin plugin = new FakePlugin();
    TestPluginLauncher launcher = new TestPluginLauncher();
    launcher.willReturn(plugin);

    PluginConfig cfg = PluginConfig.withKey("timeout", "30s");
    launcher.launch("com.example.Irrelevant", cfg);

    assertSame(cfg, plugin.configured);
    assertEquals("com.example.Irrelevant", launcher.lastLoadedName);
}

@Test
public void launchPropagatesStartupFailures() {
    TestPluginLauncher launcher = new TestPluginLauncher();
    launcher.willFailWith(new PluginStartupFailed("com.bad", new ClassNotFoundException()));

    assertThrows(PluginStartupFailed.class,
        () -> launcher.launch("com.bad", PluginConfig.empty()));
}

No real plugin classes exist in the test. No reflection runs. The launcher's coordination logic — load, configure, run, handle failure — is tested with ordinary objects, and the reflection-specific code path is the one-method seam that stays production-only.

Supporting and alternative techniques

Extract a dedicated loader class

When multiple classes in your codebase do reflective work, consolidate. A single ClassLoader-wrapper class owns all the reflection; every caller takes it as a constructor parameter. Production uses the real one; tests implement a fake loader that returns whatever objects the test wants. This is Encapsulate Global References applied to reflection specifically.

public interface ClassLoader {
    <T> T loadAndInstantiate(String name, Class<T> expectedType);
}

public class PluginLauncher {
    private final ClassLoader loader;
    public PluginLauncher(ClassLoader l) { this.loader = l; }

    public PluginResult launch(String pluginClass, PluginConfig config) {
        Plugin plugin = loader.loadAndInstantiate(pluginClass, Plugin.class);
        plugin.configure(config);
        return plugin.run();
    }
}

Real fixtures for plugin-loader-like tests

Sometimes the reflective call is the point. A test for "the launcher correctly handles a plugin whose constructor throws" might want an actual class that throws from its constructor, on the real classpath, loaded by real reflection. Write a small test-fixture class and let the test exercise the real path. Reserve the wrapping technique for the orchestration code around the reflective call — the code that decides what to load and when — and test the reflection itself separately with fixtures.

ServiceLoader for discoverable plugins

Not a testing technique, but worth noting: if reflection is being used to implement a plugin-discovery system, the JDK's java.util.ServiceLoader exists for exactly that. It's still reflection under the hood, but its API is well-defined and it integrates with module systems. Testing is still about the orchestration, not ServiceLoader itself.

Cautions and variations

Don't swallow reflection exceptions silently

When the wrapping method translates ReflectiveOperationException to a domain exception, the domain exception should carry the original as its cause. Debugging a production reflection failure without the original stack is misery. Always use the two-argument exception constructor that takes a Throwable cause.

Classes loaded for side effects are untestable through this seam

Some code uses Class.forName("com.example.Driver") specifically to trigger the class's static initializer (the old JDBC driver-loading pattern). The wrapping technique gives the test no way to simulate the static initializer running. In those cases, the reflection usage itself is a sign of a legacy pattern — look for a post-1990s alternative (ServiceLoader, explicit factory, DI container) rather than testing around it.

Generics and reflection don't mix well

The wrapping method's signature will usually have to be parameterized (<T> T load(String name, Class<T> type)) to preserve type information across the reflection. Reflection erases parameterized types — List<String>.class doesn't exist — so if the loaded objects are parameterized, the Class token is only the raw type. Document this limitation; don't pretend it's been solved.

Keep the seam tight

The extracted method should do just the reflection. Don't let it grow into a general plugin-management method with logging, caching, or retry. Keep it a seam; everything else stays in callable Java code where normal testability applies.

Related techniques not covered here. Extract and Override Call is the Ch 25 technique this page's fix instantiates. Encapsulate Global References is the deeper principle — the classloader is a global, and wrapping reflection makes that explicit.
