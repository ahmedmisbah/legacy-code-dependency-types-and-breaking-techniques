Monster-Method Dependency

Java dependency type · Chapter 25 fix: Break Out Method Object

The dependency
Monster-Method Dependency
The technique
Break Out Method Object

The dependency

A monster-method dependency is what happens when a single method has grown large enough that the dependencies within it are its local variables. The method is hundreds of lines long. Locals are declared at the top and mutated throughout. The midpoint of the method reads values that six other places have written. Pulling any piece out fails because the piece references half a dozen locals that are defined and mutated elsewhere in the same method.

The normal extract-method refactoring requires identifying inputs and outputs — what locals does the piece read, what locals does it write? In a monster method, the answer is often "all of them." Every attempt to extract produces a method with fifteen parameters and multiple out-parameters. The tangle resists decomposition.

Why this blocks tests

You can't test pieces

The method only has one public entry point. Everything interesting happens in the middle, surrounded by setup and teardown. A test can only invoke the whole thing; it can't reach in and verify one sub-computation.

Setup to exercise the whole method is enormous

Monster methods typically accept only a handful of parameters but manipulate a lot of state. To drive any particular branch deep in the method, you have to construct inputs that will cause all the earlier branches to go the way you want. Tests become Rube Goldberg machines.

Coverage is all-or-nothing

You can't get 80% of the method under test and fix 20% later. Either the whole thing runs in your test or nothing does. And if anything in the method has a problematic dependency — a static call, a file write, a network request — that dependency applies to every test of every path.

Refactoring is risky without tests

The classic chicken-and-egg: the method needs tests before you refactor it, and it needs refactoring before you can write tests. Break Out Method Object is the way out — a refactoring that is safe to apply without pre-existing tests, because it's mechanical and preserves behavior.

The technique: Break Out Method Object

Break Out Method Object promotes a single method to its own class. The method's locals become fields of the new class. The method's body stays intact, now operating on fields instead of locals. With locals turned into fields, extract-method refactorings become trivial — each extracted helper is a method on the same class, reading and writing the same fields, with zero parameters. Decomposition that was impossible inside the monster method becomes routine inside the method object.

The original method is reduced to a single line: construct the method object, call its run method (or whatever you named it), return the result. The original class and all its callers are unchanged.

When to use it

  • A method is large enough that extract-method is blocked by the tangle of locals.
  • You want to test sub-parts of the method's logic independently after decomposition.
  • Individual dependency-breaking techniques (Extract and Override Call, etc.) aren't enough because the problems are scattered throughout.

When not to use it:

  • The method is already reasonably sized — use plain extract-method instead.
  • The method is monstrous but mostly straight-line code with no branching — a linear sequence of independent steps can often be extracted directly without the method-object detour.

Example

Before — InvoiceBatch.process is a giant method with locals that every piece reads and writes:

public class InvoiceBatch {
    public BatchReport process(List<Invoice> invoices, TaxTables tax) {
        BigDecimal runningTotal = BigDecimal.ZERO;
        BigDecimal runningTax = BigDecimal.ZERO;
        int skipped = 0;
        List<String> warnings = new ArrayList<>();
        Map<String, BigDecimal> perState = new HashMap<>();

        for (Invoice inv : invoices) {
            if (inv.getTotal().signum() < 0) {
                warnings.add("negative:" + inv.getId());
                skipped++;
                continue;
            }

            BigDecimal rate = tax.rateFor(inv.getState());
            if (rate == null) {
                warnings.add("no-rate:" + inv.getState());
                skipped++;
                continue;
            }

            BigDecimal lineTax = inv.getTotal().multiply(rate);
            runningTax = runningTax.add(lineTax);
            runningTotal = runningTotal.add(inv.getTotal()).add(lineTax);

            perState.merge(inv.getState(), inv.getTotal(), BigDecimal::add);
            // ... 80 more lines of similar logic ...
        }

        BigDecimal avg = skipped < invoices.size()
            ? runningTotal.divide(new BigDecimal(invoices.size() - skipped), RoundingMode.HALF_UP)
            : BigDecimal.ZERO;

        return new BatchReport(runningTotal, runningTax, skipped, warnings, perState, avg);
    }
}

Every sub-computation (validation, rate lookup, line-tax calculation, running-total update, per-state accumulation, final averaging) reads and writes the same shared locals. Pulling one out means passing five parameters in and returning four values.

Steps

  1. Create a new class named for the operation: InvoiceBatchProcessor. Give it a constructor that accepts the original method's parameters.
  2. Copy every local variable of the original method to a field on the new class.
  3. Copy the body of the original method into a method on the new class (typically named run, process, or execute), adjusting local references to field references.
  4. Have the method return whatever the original method returned.
  5. Replace the original method's body with a single line: return new InvoiceBatchProcessor(invoices, tax).run();.
  6. Now that locals are fields, extract coherent pieces into their own methods freely. The extracted methods have no parameters — they operate on the shared fields.
  7. Write tests for the new class, both end-to-end and against the extracted helpers where useful.

Example (after)

public class InvoiceBatchProcessor {
    private final List<Invoice> invoices;
    private final TaxTables tax;

    // former locals, now fields
    private BigDecimal runningTotal = BigDecimal.ZERO;
    private BigDecimal runningTax = BigDecimal.ZERO;
    private int skipped = 0;
    private final List<String> warnings = new ArrayList<>();
    private final Map<String, BigDecimal> perState = new HashMap<>();

    public InvoiceBatchProcessor(List<Invoice> invoices, TaxTables tax) {
        this.invoices = invoices;
        this.tax = tax;
    }

    public BatchReport run() {
        for (Invoice inv : invoices) {
            if (!accept(inv)) continue;
            applyLine(inv);
        }
        return buildReport();
    }

    private boolean accept(Invoice inv) {
        if (inv.getTotal().signum() < 0) {
            warnings.add("negative:" + inv.getId());
            skipped++;
            return false;
        }
        if (tax.rateFor(inv.getState()) == null) {
            warnings.add("no-rate:" + inv.getState());
            skipped++;
            return false;
        }
        return true;
    }

    private void applyLine(Invoice inv) {
        BigDecimal lineTax = inv.getTotal().multiply(tax.rateFor(inv.getState()));
        runningTax = runningTax.add(lineTax);
        runningTotal = runningTotal.add(inv.getTotal()).add(lineTax);
        perState.merge(inv.getState(), inv.getTotal(), BigDecimal::add);
    }

    private BatchReport buildReport() {
        BigDecimal avg = skipped < invoices.size()
            ? runningTotal.divide(new BigDecimal(invoices.size() - skipped), RoundingMode.HALF_UP)
            : BigDecimal.ZERO;
        return new BatchReport(runningTotal, runningTax, skipped, warnings, perState, avg);
    }
}

// The original class becomes a thin wrapper
public class InvoiceBatch {
    public BatchReport process(List<Invoice> invoices, TaxTables tax) {
        return new InvoiceBatchProcessor(invoices, tax).run();
    }
}

@Test
public void skipsNegativeInvoicesAndRecordsWarning() {
    InvoiceBatchProcessor p = new InvoiceBatchProcessor(
        List.of(Invoice.of("I-1", new BigDecimal("-10"), "CA")),
        TaxTables.withRates(Map.of("CA", new BigDecimal("0.1"))));

    BatchReport report = p.run();

    assertEquals(1, report.getSkipped());
    assertEquals(List.of("negative:I-1"), report.getWarnings());
}

Each extracted helper (accept, applyLine, buildReport) is short, has no parameters, and is easy to read. Because they all operate on fields, more aggressive decomposition becomes possible later without the parameter-list explosion that blocked it inside the original method.

Supporting and alternative techniques

Expose Static Method

Sometimes inside the monster method you find a block that doesn't touch any locals — a piece of pure computation sitting in the middle of the tangle. That block doesn't need the full method-object treatment. Extract it as a static method that takes its inputs as parameters, returns its outputs, and can be tested in isolation. A method-object refactor often surfaces several such opportunities after the main extraction is done.

Extract and Override Call (inside the method object)

Once the monster method is a class, every dependency-breaking technique in the catalog applies to it just like any other class. If the method object makes a problematic call (a network request, a file write), apply Extract and Override Call on it exactly as you would on any ordinary class.

Cautions and variations

Preserve behavior during the promotion

The promotion itself should not change behavior. Locals become fields, but the code path stays identical. Resist the temptation to fix bugs, rename variables, or restructure branches until the method object exists and tests are in place. Mix one kind of change at a time.

Watch out for closure over the outer class

If the monster method accesses fields or methods of the class it was on, the method object needs access to those too. Either pass the outer object in as a constructor argument, or extract the pieces the method uses (via Extract Interface or simple delegation) so the method object depends on something narrower than the whole outer class.

One method object per method

It's tempting to consolidate: "I have two monster methods, let me make one BatchOperations class with both." Resist. A method object embodies the state of exactly one method. Two methods together produce a new blended class with all the entanglement risks the original methods had. Keep them separate.

Final constants aren't locals

Constants declared at the top of the method (final int MAX = 10) don't need to become fields; they can be constants of the new class. Distinguish between mutable working state (becomes fields) and read-only configuration (becomes constants or constructor parameters).

Related techniques not covered here. For a dependency that's concentrated at a single call rather than spread through a method, Extract and Override Call is the surgical tool. For a class full of monster methods (rather than one method inside an otherwise reasonable class), consider applying Push Down Dependency to the class first — sometimes a "monster method" is really "one method that couldn't be tested because its class couldn't be constructed in tests."
