Network / Protocol Dependency

Java dependency type · Modern Java technique: Extract a Client Adapter

The dependency
Network / Protocol Dependency
The technique
Extract a Client Adapter
Not in Chapter 25. Feathers discusses network concerns in chapters 14 and 15 as a motivating example — code that talks to a server is hard to test, so wrap it — but doesn't provide a named Chapter 25 technique. The closest cataloged move is Adapt Parameter, which covers it generically. This pairing gives the network-specific shape its own page because the tooling (WireMock, MockWebServer, vendor sandbox environments) and trade-offs (integration vs unit testing) are distinct enough to warrant explicit treatment.

The dependency

A network / protocol dependency exists when code speaks directly to a remote system over a protocol — HTTP via HttpClient or OkHttpClient; REST via retrofit-style generated clients; GraphQL via a vendor library; gRPC via generated stubs; raw TCP sockets; JDBC; SMTP; a vendor SDK (AWS, Stripe, Twilio, Slack) that bundles its own HTTP layer. The network call is buried inside the class's methods, with whatever serialization, authentication, retry, and connection-management details the chosen library requires.

Unlike a generic library dependency, network code has a distinctive testing challenge: the collaborator is not present at test time in any reasonable sense. You can't instantiate it (it's a remote service), you can't predict its availability, and you can't easily simulate its failure modes. The classical dependency-breaking techniques all apply, but they apply against a backdrop of "the real thing lives on someone else's server".

Why this blocks tests

The collaborator isn't in the JVM

Every other dependency type this site covers is an object in your process. A network dependency is a process somewhere else — or, worse, a business that charges you money every time your test accidentally calls it. Tests need to avoid ever letting the call escape the JVM.

Real HTTP in tests is slow and flaky

Even when the remote service is cooperative (a staging environment, a sandbox account), every network round-trip adds latency. Tests that hit real HTTP take seconds each and fail when the network is slow, when DNS is flaky, or when the remote service is briefly down. The feedback loop degrades exactly the way it does with filesystem I/O, just worse.

Error paths require specific server behavior

Testing "what happens when the server returns 503?" means getting a real server to return 503. Testing "what happens when the response JSON is malformed?" means a real server that sends malformed JSON. Testing "what happens if the connection drops mid-response?" means a network layer that drops connections. None of these are easy with a live remote.

Vendor SDK clients are often final or heavy

AWS SDK's S3Client, Stripe's Stripe static facade, Twilio's RestClient — many of these are final classes or have heavy constructors that set up connection pools, authentication, and protocol state. Your test needs a way around the SDK boundary, either by not touching it at all or by interposing at the HTTP layer beneath it.

Authentication couples tests to credentials

A test that creates a real client needs real credentials. Real credentials either live in environment variables (fragile, platform-specific) or in test fixtures (which get accidentally committed). The best tests have no credentials at all, because they never make network calls.

The technique: Extract a Client Adapter

Extract a Client Adapter defines a small interface capturing exactly the operations your code performs against the remote service — not "everything the HTTP client can do", but "the three calls my class actually makes". The interface uses your domain types, not protocol types. The production implementation owns the real network client and translates between your domain types and the protocol's wire format. Tests implement the interface directly with fakes that return canned domain objects.

This is Adapt Parameter applied deliberately to a network boundary, with one specific discipline: the interface's methods return your domain types, not the protocol library's types. The line between "your code" and "the protocol" runs through the adapter, not through the interface. If the vendor changes its library, the adapter changes; your code and your tests don't.

When to use it

  • Code directly uses an HTTP client, a gRPC stub, or a vendor SDK.
  • Tests need deterministic behavior without real network calls.
  • The class under test uses a small number of operations against the remote — a dozen endpoints, not a hundred.

When not to use it:

  • You want to test the wire-format handling itself (parsing specific response bodies, authentication headers, retry semantics) — use a fake HTTP server like WireMock or MockWebServer instead. These exercise the real client library but with a server under the test's control.
  • The class uses a very wide slice of the remote API — a hundred endpoints — and maintaining an interface with that many methods is itself a cost. Consider splitting the class or accepting that integration tests with a fake server carry more of the weight.

Example

Before — UserEnricher calls a REST API using HttpClient directly:

public class UserEnricher {
    private static final String BASE_URL = "https://profile.example.com";
    private final HttpClient http;
    private final String apiToken;
    private final ObjectMapper json = new ObjectMapper();

    public UserEnricher(String apiToken) {
        this.http = HttpClient.newHttpClient();
        this.apiToken = apiToken;
    }

    public EnrichedUser enrich(User user) throws IOException, InterruptedException {
        HttpRequest req = HttpRequest.newBuilder()
            .uri(URI.create(BASE_URL + "/users/" + user.getId()))
            .header("Authorization", "Bearer " + apiToken)
            .GET().build();

        HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString());
        if (resp.statusCode() == 404) return EnrichedUser.minimal(user);
        if (resp.statusCode() >= 500) throw new ProfileServiceUnavailable();

        ProfileJson profile = json.readValue(resp.body(), ProfileJson.class);
        return user.enrichedWith(profile.preferences, profile.segments);
    }
}

Testing enrich's logic — fallback on 404, error on 5xx, merging enrichment data — requires a real profile service or a way to control HTTP responses. Both are much bigger than the logic itself.

Steps

  1. List the operations the class performs against the remote. Here: fetch a profile by user ID. Just one.
  2. Define an interface with methods that use your domain types. Method signatures should look like business operations, not HTTP calls.
  3. Represent remote-specific error conditions (404, 5xx) either as distinct result types (sealed interface, Optional) or as domain exceptions. Don't leak HTTP status codes into the interface.
  4. Implement the interface with a client adapter that owns the real HTTP client, builds requests, parses responses, and translates errors.
  5. Change the original class to depend on the interface via constructor injection.
  6. In tests, implement the interface directly with fakes.

Example (after)

// Interface you own, in domain terms
public interface ProfileService {
    Optional<UserProfile> fetchProfile(String userId);
}

// Adapter — owns the HTTP client and the JSON
public class HttpProfileService implements ProfileService {
    private final HttpClient http;
    private final String baseUrl;
    private final String apiToken;
    private final ObjectMapper json = new ObjectMapper();

    public HttpProfileService(HttpClient http, String baseUrl, String apiToken) {
        this.http = http; this.baseUrl = baseUrl; this.apiToken = apiToken;
    }

    @Override
    public Optional<UserProfile> fetchProfile(String userId) {
        try {
            HttpResponse<String> resp = http.send(
                HttpRequest.newBuilder()
                    .uri(URI.create(baseUrl + "/users/" + userId))
                    .header("Authorization", "Bearer " + apiToken)
                    .GET().build(),
                HttpResponse.BodyHandlers.ofString());

            if (resp.statusCode() == 404) return Optional.empty();
            if (resp.statusCode() >= 500) throw new ProfileServiceUnavailable();

            ProfileJson p = json.readValue(resp.body(), ProfileJson.class);
            return Optional.of(new UserProfile(p.preferences, p.segments));
        } catch (IOException | InterruptedException e) {
            throw new ProfileServiceUnavailable(e);
        }
    }
}

// Code under test takes the interface
public class UserEnricher {
    private final ProfileService profiles;

    public UserEnricher(ProfileService profiles) { this.profiles = profiles; }

    public EnrichedUser enrich(User user) {
        return profiles.fetchProfile(user.getId())
            .map(p -> user.enrichedWith(p.getPreferences(), p.getSegments()))
            .orElseGet(() -> EnrichedUser.minimal(user));
    }
}

// Test — no HTTP, no JSON parsing, no credentials
class FakeProfileService implements ProfileService {
    public String lastRequestedId;
    private Optional<UserProfile> next = Optional.empty();
    private RuntimeException nextError;

    public void willReturn(UserProfile p) { this.next = Optional.of(p); this.nextError = null; }
    public void willReturnNotFound() { this.next = Optional.empty(); this.nextError = null; }
    public void willFailWith(RuntimeException e) { this.nextError = e; }

    @Override
    public Optional<UserProfile> fetchProfile(String userId) {
        this.lastRequestedId = userId;
        if (nextError != null) throw nextError;
        return next;
    }
}

@Test
public void enrichMergesProfilePreferencesAndSegments() {
    FakeProfileService profiles = new FakeProfileService();
    profiles.willReturn(new UserProfile(Map.of("theme", "dark"), Set.of("premium")));

    EnrichedUser enriched = new UserEnricher(profiles).enrich(User.withId("u-42"));

    assertEquals("dark", enriched.getPreference("theme"));
    assertTrue(enriched.inSegment("premium"));
    assertEquals("u-42", profiles.lastRequestedId);
}

@Test
public void enrichFallsBackToMinimalWhenProfileMissing() {
    FakeProfileService profiles = new FakeProfileService();
    profiles.willReturnNotFound();

    EnrichedUser enriched = new UserEnricher(profiles).enrich(User.withId("u-unknown"));

    assertTrue(enriched.isMinimal());
}

@Test
public void enrichPropagatesServiceFailures() {
    FakeProfileService profiles = new FakeProfileService();
    profiles.willFailWith(new ProfileServiceUnavailable());

    assertThrows(ProfileServiceUnavailable.class,
        () -> new UserEnricher(profiles).enrich(User.withId("u-1")));
}

Supporting and alternative techniques

WireMock for HTTP integration tests

The adapter you wrote is itself untested by the unit tests above — they bypass it entirely. To cover the adapter's HTTP behavior (URL construction, header formatting, JSON parsing, status-code handling), spin up WireMock, MockWebServer (Square's), or a similar in-process HTTP server in integration tests. The tests drive your real HttpProfileService against the fake server and verify it makes the correct requests and interprets the correct responses.

@Test
public void httpClientSendsBearerToken() {
    wireMock.stubFor(get(urlPathEqualTo("/users/u-1"))
        .willReturn(ok().withBody("{ ... }")));

    new HttpProfileService(HttpClient.newHttpClient(), wireMock.baseUrl(), "secret")
        .fetchProfile("u-1");

    wireMock.verify(getRequestedFor(urlEqualTo("/users/u-1"))
        .withHeader("Authorization", equalTo("Bearer secret")));
}

These integration tests are slower than unit tests (WireMock sets up a real HTTP server) but vastly faster and more reliable than hitting a real remote.

Vendor sandbox environments

Services like Stripe, Twilio, and AWS provide sandbox or test accounts with non-production endpoints. Integration tests can hit the sandbox to verify the real client library works against the real wire format. Keep these tests few, tagged separately, and run them outside the normal unit-test cycle. Don't use sandbox credentials in every test run.

Contract testing

For systems where your adapter needs to stay in sync with a remote service you don't control, contract testing (Pact, Spring Cloud Contract) lets you agree on the wire format once and verify both sides. Not a Chapter 25 technique and not a replacement for unit or integration tests — but it helps the adapter stay honest as the remote evolves.

Adapt Parameter (the Ch 25 sibling)

The generic form of this page. Read that one if the remote collaborator looks more like "a library with a Java API" and less like "something at the end of an HTTP connection". The mechanical fix is the same; the motivation differs.

Cautions and variations

Keep protocol types out of the interface

If the interface's methods return HttpResponse or JsonNode or vendor SDK types, you haven't really abstracted the network — you've just moved the HTTP code one level up. The test point: given an interface, can you write a non-HTTP implementation in a few lines? If no, your interface still carries protocol concerns.

One interface per remote, not one per call

A system with twelve calls against the profile service wants one ProfileService interface with twelve methods, not twelve interfaces. Group by the remote being called; each remote is one abstraction. Over-decomposing produces test setup that drowns in fakes.

Decide where retries live

Retries with exponential backoff often belong in the adapter (it knows about protocol-level transient failures). Sometimes they belong in the caller (business-logic-level "try harder" semantics). Either place is defensible; a clear decision matters. Don't let retries happen at both levels silently — you'll get an N2 retry explosion under real failures.

Fakes aren't contracts

A fake that returns canned responses verifies your code's behavior given certain responses. It doesn't verify that the remote actually produces those responses. Keep a small set of integration tests (or contract tests) that bind the adapter to the real protocol shape. Unit tests alone can pass while production is broken.
