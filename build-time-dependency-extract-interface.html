Build-Time Dependency

Java dependency type · Chapter 25 fix: Extract Interface

The dependency
Build-Time Dependency
The technique
Extract Interface

The dependency

A build-time dependency is the kind that doesn't prevent a test from passing — it prevents the test cycle from being fast enough to run often. Clients depend on a concrete class that changes frequently. Every time the class's source is edited, the compiler treats every client that imports it as potentially out of date. Incremental builds recompile large swaths of the codebase; CI builds recompile even more. The feedback loop from "save file" to "test result" stretches from seconds into minutes.

This is the one Feathers dependency type where the problem isn't testability in isolation — it's testability in practice. A test suite that runs in two seconds gets run after every change; a test suite that requires a three-minute build gets run rarely, and the tests it contains stop being useful.

Why this blocks tests

The build is now a bottleneck

Tests are only useful if they're run often. If the build must complete before any test runs, and the build is slow because a core concrete class has many dependents, tests that pass in milliseconds still appear to take minutes. Developers start running them less often.

Changes ripple through the dependency graph

In Java, a client that imports com.example.OrderService is compiled against the binary signature of OrderService. Changing private internals shouldn't trigger recompilation of clients — and often doesn't, thanks to incremental build tools — but changing public methods, adding fields referenced from initializers, or modifying the class hierarchy does. Clients compile even when they didn't need to.

Mocking is harder than it should be

If clients depend on a concrete class, test doubles for that class have to subclass it — which means they inherit the class's real constructor cost, its fields, and potentially its side effects. An interface-based dependency lets the test double start from zero.

Coupling hides from the compiler

A concrete dependency couples callers to the shape of the implementation: the constructor signature, the full set of public methods, sometimes even the package layout. The compiler can't help you decouple those — the whole concrete surface is part of the contract. An interface makes the contract explicit.

A different motivation, the same technique. Extract Interface is usually sold as a testability move — it breaks runtime dependencies. For build-time dependencies, the motivation shifts to compile-time speed, but the mechanics are identical. The interface is a stable compile-time contract, and implementation changes no longer force downstream recompilation.

The technique: Extract Interface

Extract Interface creates a new interface declaring the methods that clients use on the concrete class. Clients are updated to depend on the interface. The concrete class is declared to implement the interface. Production continues to use the concrete implementation; the difference is that clients are now compiled against the interface, and changes to the implementation no longer invalidate client compilation units.

For this application, the goal is to make the interface as stable as possible — precisely because instability in the interface is exactly what you're trying to avoid. The interface captures what the class does; the implementation keeps how. Only changes to the what cause client recompilation.

When to use it

  • A concrete class has many dependents and changes frequently.
  • Build time — incremental or full — has become a bottleneck for the team's development cycle.
  • You control the class and can add an interface without coordinating across teams.

When not to use it:

  • The class is stable and rarely changes — extraction adds ceremony for no gain.
  • The class has few dependents — the recompilation cost is already bounded.
  • The interface would have to change nearly as often as the class — you haven't separated the what from the how.

Example

Before — PricingEngine is imported directly by many client classes:

public class PricingEngine {
    private final PriceCache cache = new PriceCache();
    private DiscountStrategy strategy;

    public Money finalPrice(Order order, Customer c) { /* ... */ }
    public Money lineItemPrice(LineItem item) { /* ... */ }
    public void setStrategy(DiscountStrategy s) { this.strategy = s; }
}

// Dozens of clients
public class CheckoutController {
    private final PricingEngine pricing; // concrete dependency
    // ...
}
public class CartRenderer {
    private final PricingEngine pricing; // concrete dependency
    // ...
}
public class BatchInvoicer {
    private final PricingEngine pricing; // concrete dependency
    // ...
}

When PricingEngine is edited — new private field, new helper method, a change to lineItemPrice's internals — every client's compilation unit may be invalidated. In a large project, that's minutes of build time per change.

Steps

  1. List the methods clients actually call on the concrete class. In most cases this is a subset of its public methods — utility methods used only internally stay off the interface.
  2. Create an interface with those methods. Name it for the role (Pricing, PriceSource) rather than for the class (IPricingEngine).
  3. Declare the concrete class to implement the interface. No body changes needed — the class already has the methods.
  4. Update each client to declare its dependency as the interface type, not the concrete class type. This is a mechanical change — replace PricingEngine with Pricing in field declarations, parameters, and local variables.
  5. At composition roots (factory methods, constructors called from main, DI configuration), keep the concrete class — that's where the real implementation is created.

Example (after)

// The stable contract
public interface Pricing {
    Money finalPrice(Order order, Customer c);
    Money lineItemPrice(LineItem item);
}

// The implementation — free to change without triggering client recompilation
public class PricingEngine implements Pricing {
    private final PriceCache cache = new PriceCache();
    private DiscountStrategy strategy;

    @Override public Money finalPrice(Order order, Customer c) { /* ... */ }
    @Override public Money lineItemPrice(LineItem item) { /* ... */ }
    public void setStrategy(DiscountStrategy s) { this.strategy = s; }
}

// Clients now depend on the interface
public class CheckoutController {
    private final Pricing pricing;
    public CheckoutController(Pricing pricing) { this.pricing = pricing; }
    // ...
}

// Composition root creates the concrete implementation once
public class AppBootstrap {
    public static void main(String[] args) {
        Pricing pricing = new PricingEngine();
        new CheckoutController(pricing).start();
    }
}

Now when PricingEngine gains a new private helper, adjusts cache sizing, or restructures finalPrice's internals, the Pricing interface is unchanged and none of the clients need recompilation. Only the composition root and the engine itself compile.

Supporting and alternative techniques

Extract Implementer

A C++ technique with less relevance in Java but worth noting. Where Extract Interface adds a new type above the existing class, Extract Implementer renames the existing class to XImpl and turns the original name into the interface. The effect is similar, but clients that referenced the original class name don't have to change. In Java, modern refactoring tools make Extract Interface equally painless either way, so Extract Implementer is rarely the right call.

Package boundaries

Not a Chapter 25 technique, but a close relative that can compound the benefit. Put the interface in a stable package (say, com.example.pricing.api) and the implementation in a volatile one (com.example.pricing.impl). Build systems can use this separation to short-circuit recompilation of dependents when only .impl files changed. Combined with Extract Interface, it's the standard way large Java codebases keep build times manageable.

Module boundaries (JPMS or build modules)

At the extreme, split the interface and implementation into separate build modules (Gradle subprojects, Maven modules, or JPMS modules). Clients depend on the interface module; the implementation module depends on the interface module and provides the binding. Build tools recompile only modules whose inputs changed, so edits inside the implementation module don't trigger any recompilation in client modules. This is overkill for small codebases but pays off quickly once the project has a dozen teams and a hundred modules.

Cautions and variations

The interface must be stable

If the interface changes every time the implementation does, you've added ceremony without solving the problem. Design the interface around durable concepts: what does this type do? rather than how does this type do it?. Private helpers, caches, strategies — none of those belong on the interface.

Minimal surface

Include only the methods clients actually use. A class with fifteen public methods might need only six on the interface. The narrower the interface, the less often it needs to change, and the easier it is to reason about.

Don't extract before you need to

Premature interface extraction adds noise. Wait until the class has multiple clients and the pain of rebuilds is concrete. Feathers' "extract when it helps" applies here too.

Dependency Inversion as a byproduct

After this refactor, high-level modules (clients) depend on an abstraction (the interface) rather than a low-level module (the concrete implementation). That's the Dependency Inversion Principle — and Extract Interface is one of the most direct ways to achieve it on an existing codebase. The build-time benefit and the design benefit arrive together.
